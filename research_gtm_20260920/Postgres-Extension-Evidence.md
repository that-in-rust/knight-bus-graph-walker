# PostgreSQL Extension Feasibility and Distribution Evidence

Retrieval date: **2026-09-20** (`retrieval2026-09-20`).

Status: **Evidence draft finalized for handoff at the user's stop request.** No extension was built, installed, benchmarked, or tested on a customer host. Remaining gaps are explicit below. This document supplies technical and distribution evidence; the main lead owns product/GTM synthesis. No pgvector adoption research is included.

## Premise Check

The question is whether an OSS native PostgreSQL extension is both a feasible implementation vehicle and an installable delivery vehicle for Knight Bus's bounded graph analytics. These are different tests. SQL familiarity, database popularity, permission to issue `CREATE EXTENSION`, and permission to put a new native library on the database server are not interchangeable.

The local [decision brief](/Users/amuldotexe/Desktop/personal-repos-lane/knight-bus-graph-walker/research_4gb_20260919/Final-Research-Decision-Brief.md) and [workflow](/Users/amuldotexe/Desktop/personal-repos-lane/knight-bus-graph-walker/research_4gb_20260919/End-To-End-Workflow.md) define the inherited contract: one useful supported analytical job, consistent input, preparation, query, complete usable output, and refresh. The target is a **4,000,000,000-byte physical machine**, not a 4 GB algorithm heap. A provisional 3 GB worker allowance plus 1 GB reserve is an unmeasured design assumption. The 50 GB retained-prepared allowance is distinct from input size and peak live disk. These documents do not establish a completed source-to-answer 4 GB implementation.

Evidence labels:

- **Fact:** directly supported by the linked primary documentation or repository evidence retrieved in this research.
- **Inference:** an engineering or distribution consequence, not a measured Knight Bus result.
- **Unknown:** unresolved by the inspected sources or requiring implementation/customer-host verification.

Lenses used: PostgreSQL extension engineering, managed-host operations, lifecycle resource accounting, and a skeptical installation/maintenance review. No additional agents were created.

## Candidate Approaches

| Delivery shape | Where computation actually runs | Installation and resource consequences |
| --- | --- | --- |
| Native pgrx extension | Inside a PostgreSQL backend for ordinary UDF calls | Native server artifact and operator approval required; database and kernel allocations share the host budget. |
| PostgreSQL background worker | Separate process managed by PostgreSQL, with access to its shared memory | Still native extension deployment, not an external isolation boundary. Static and dynamic registration mechanisms exist. [PG background workers](https://www.postgresql.org/docs/18/bgworker.html) |
| SQL/trusted-language package | In PostgreSQL through the installed language runtime | Can avoid distributing a customer-supplied native library, but cannot assume arbitrary filesystem, FFI, threading, or server-hook access. [PL/Rust trust model](https://plrust.io/plrust.html), [pg_tle](https://github.com/aws/pg_tle) |
| External job with results imported | Customer-run process/container reads a consistent projection, prepares and computes, then writes ordinary result rows | Does not require Knight Bus native code on the database host. Same-machine placement still shares 4 GB; remote placement adds separately charged compute and transfer. This is a proposed Knight Bus integration, not an implemented feature. |
| Thin SQL interface plus external worker | SQL tables/functions describe jobs or expose completed results; heavy work remains external | Potentially preserves SQL consumption and ordinary database access controls. A native wrapper would retain the native installation gate; ordinary SQL tables plus a polling client need not. Inference, not a verified deployment. |

**Working thesis, not GTM selection:** native extension development is credible, but extension-only distribution cannot be equated with reaching all PostgreSQL users. Preserve the distinction between an in-database engine, a trusted-language implementation, and an external PostgreSQL-connected job in any subsequent product decision.

## Native Engineering Evidence

### Rust and Packaging

**Fact:** pgrx exposes Rust functions to PostgreSQL, provides SPI and memory-context interfaces, and offers multi-version testing and packaging. Its retrieved development README advertises PostgreSQL 13-18 plus 19beta1, not a guarantee that any chosen released pgrx version supports every listed target. The separately retrieved API documentation identifies pgrx **0.19.1**, dated June 23, 2026. Pin and test the release actually selected. [pgrx README](https://github.com/pgcentralfoundation/pgrx), [0.19.1 API](https://docs.rs/pgrx/latest/pgrx/memcxt/index.html)

**Fact:** the README requires a Rust toolchain, libclang and relevant native build dependencies, has no MSRV policy, and warns about unresolved unsafe-wrapper soundness questions. It says auxiliary threads must not call internal PostgreSQL functions or use PostgreSQL-provided pointers; async interaction remains unexplored. Rust memory safety is not a database sandbox. [pgrx requirements and caveats](https://github.com/pgcentralfoundation/pgrx#caveats--known-issues)

**Fact:** `cargo pgrx package` produces an installation package directory; `install` targets PostgreSQL identified by `pg_config`. This is not automatic publication to Linux repositories or inclusion by managed providers. PostgreSQL's PGXS documentation likewise distinguishes compilation and placement of shared modules, control files and SQL files. [cargo-pgrx](https://github.com/pgcentralfoundation/pgrx/blob/develop/cargo-pgrx/README.md), [PGXS](https://www.postgresql.org/docs/18/extend-pgxs.html)

**Inference: distribution prerequisites for Knight Bus:** maintain a declared PostgreSQL-major/OS/CPU/runtime-library matrix; reproducible native builds; extension control and SQL installation/update files; runtime dependency and license manifests; checksums; regression/upgrade/restore tests; and an operator-facing support policy. Test the actual host build, especially PostgreSQL forks. Prebuilt binaries can remove the customer's compiler requirement without removing their native-code approval requirement. None of these release artifacts was verified for Knight Bus here.

### Memory: What the Docs Actually Establish

| Evidence | Consequence for a bounded graph engine |
| --- | --- |
| PostgreSQL documents C-function allocation and memory-context lifetimes; SPI has its own allocation context, cleaned up by `SPI_finish`. pgrx supplies explicit memory-context interfaces. [C functions](https://www.postgresql.org/docs/18/xfunc-c.html), [SPI memory](https://www.postgresql.org/docs/18/spi-memory.html), [pgrx memory contexts](https://docs.rs/pgrx/latest/pgrx/memcxt/index.html) | Ownership/lifetime management is necessary, but does not establish a numerical whole-query limit. Audit every PostgreSQL allocation, Rust collection and foreign-library allocation. Do not assume all Rust heap allocation is automatically charged to a PostgreSQL context or Knight Bus quota. Exact allocator integration remains unverified. |
| PG18 `work_mem` applies to individual operations such as sorts/hashes; concurrent operations/sessions multiply usage. Hash operations use `work_mem * hash_mem_multiplier`. Maintenance and autovacuum have separate settings. [PG18 resource settings](https://www.postgresql.org/docs/18/runtime-config-resource.html) | **No inspected evidence makes `work_mem` a universal native-extension heap cap.** A specific extension may voluntarily use it or integrate with spill-aware executor facilities. A custom graph heap/spill schedule must be inspected and measured. |
| `temp_file_limit` is per PostgreSQL process and excludes explicit temporary tables. [PG18 disk settings](https://www.postgresql.org/docs/18/runtime-config-resource.html#RUNTIME-CONFIG-RESOURCE-DISK) | It is not a whole-host disk allowance. Do not assume arbitrary extension-owned files participate in it; establish the file APIs and accounting used. |
| `pg_backend_memory_contexts` describes the current backend's memory contexts. [PG18 monitoring view](https://www.postgresql.org/docs/18/view-pg-backend-memory-contexts.html) | Useful attribution, not a complete physical-host measurement or proof that external heaps, all other backends and kernel memory are included. |
| `SPI_cursor_fetch` takes a row count and exposes fetched tuples through SPI. [SPI cursor fetch](https://www.postgresql.org/docs/18/spi-spi-cursor-fetch.html) | Incremental extraction is possible, but a row limit is not a byte bound when values are variable-width. Bound tuple lifetimes, decoding, queues and oversized values. |

**Unknown:** whether a proposed Knight Bus implementation uses PostgreSQL-managed spilling, its own disk representation, custom allocators, mmap, or a foreign numerical library. Therefore neither "PostgreSQL bounds extension memory automatically" nor "PostgreSQL extensions must load the whole graph into RAM" is supported. Storage and execution design, not the extension label, determines that behavior.

### Parallelism, Security and Lifecycle

**Fact:** user-defined functions default to `PARALLEL UNSAFE`. Writes, transaction-state changes and certain persistent setting changes require unsafe classification; temporary tables, cursors and unsynchronized backend-local state require restricted classification. Incorrect labeling can cause wrong answers or undefined native-code behavior. `PARALLEL SAFE` is permission for planner placement, not an implementation of parallel graph execution. [PG18 parallel safety](https://www.postgresql.org/docs/18/parallel-safety.html)

**Fact:** PostgreSQL background workers are server-managed processes, can access shared memory, have limited worker slots, and carry explicit robustness/security warnings. Workers can be registered at server start or dynamically; therefore not every worker design universally requires a startup preload. A particular extension's initialization requirements must be checked. [PG18 background workers](https://www.postgresql.org/docs/18/bgworker.html)

**Fact:** extension installation/update scripts and SQL functions have search-path attack surfaces. `SECURITY DEFINER` requires careful ownership, safe name resolution and privilege handling. [Extension security](https://www.postgresql.org/docs/18/extend-extensions.html#EXTEND-EXTENSIONS-SECURITY), [CREATE FUNCTION security](https://www.postgresql.org/docs/18/sql-createfunction.html#SQL-CREATEFUNCTION-SECURITY)

**Inference: acceptance gates before native deployment:** preserve caller authorization for source projections and stored results; never treat a persisted graph snapshot as an authorization bypass; bound simultaneous jobs across sessions and workers; integrate cooperative cancellation into long-running native loops; test transaction abort, backend failure, disk exhaustion and slow consumers. Audit generation publication, stale readers, file cleanup, backup/restore and failover. Files written outside normal database storage must not be assumed to inherit PostgreSQL WAL, physical replication or backup coverage. Exact cancellation and custom-file durability APIs were not investigated to completion.

## Four Meanings of Trusted

1. **Packaged extension marked `trusted`:** PostgreSQL's control-file property allows a non-superuser with database `CREATE` privilege to install an already available extension under defined ownership rules. This can include native components; it does not sandbox those components or deliver missing server files. [Extension control parameters](https://www.postgresql.org/docs/18/extend-extensions.html)
2. **Trusted procedural language:** restricts what user-authored functions can do. This is not the same as merely writing ordinary native Rust. Trusted PL/Rust restricts host/filesystem access and exposes a constrained pgrx interface. [PL/Rust model](https://plrust.io/plrust.html)
3. **Trusted Language Extensions (`pg_tle`):** an installed framework for registering and managing extensions in environments without customer filesystem access, using supported trusted languages. It is not a loader for an arbitrary customer-supplied pgrx `.so`. Selected hooks exposed by the framework do not imply arbitrary PostgreSQL hook access. [pg_tle project](https://github.com/aws/pg_tle), [RDS TLE overview](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/PostgreSQL_trusted_language_extension.html)
4. **Provider-approved or delegated extension:** a hosting/provider permission and support policy. Delegating installation to a database role does not expand the provider's native library catalog. [RDS delegated support](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/RDS_delegated_ext.html)

**Inference:** SQL-only orchestration or a sufficiently restricted algorithm could be distributed as a TLE. Porting Knight Bus's proposed disk-backed native kernel into that environment is a separate feasibility project, not a packaging conversion.

### Important Corrections to Older Advice

- **RDS PL/Rust is not a forward-compatible escape hatch:** the current AWS guide explicitly ends support starting with **PostgreSQL 18**. The RDS overview lists TLE floors of 13.12, 14.5, 15.2, 16.1, 17.1 and 18.1 on their respective branches. Use that overview for concepts and the exact version table/server for deployed versions. - **Supabase hosted version pinning changed:** July 22, 2026 changelog says that from August 5, explicit extension versions requested by ordinary users are ignored in favor of the project's default, with a warning; future rejection was separately planned. Existing installed versions and self-hosted deployments are not affected by that announced change. Verify `extversion` after installation; successful SQL is not proof the requested version was honored. [Supabase version policy](https://supabase.com/changelog/extension-version-pinning-ignored)
- **dbdev is a TLE registry/tool, not arbitrary native distribution:** current dbdev docs deprecate the in-database client, recommend CLI-generated installation SQL in migrations, and warn that logical restore with TLEs can fail. Older Supabase examples use the in-database client. Resolve that discrepancy and test restore before shipping an onboarding recipe. [Current dbdev docs](https://supabase.github.io/dbdev/), [older launch article](https://supabase.com/blog/dbdev)

## Customer Installation Journey

These are proposed acceptance steps, not commands executed or a currently supported Knight Bus installer.

1. **Identify the actual destination:** hosted provider versus self-managed; exact PostgreSQL major/minor and image; CPU/runtime; database administrator; allowed native catalog; maintenance authority. Check `pg_available_extensions`, `pg_available_extension_versions` and installed `pg_extension`, plus host policy. An available extension and an installed extension are different states. [Packaging and installation](https://www.postgresql.org/docs/18/extend-extensions.html)
2. **Choose a genuinely installable route:** self-managed operators can deploy a tested native package/image. A managed customer cannot proceed merely by granting database privileges if the native artifact is unavailable. For TLE, first establish the provider-installed framework, supported language and administrative grants. For an external worker, establish network access, export authorization and destination write permissions.
3. **Complete the operator gate:** security/dependency review, package verification, backup and rollback rehearsal, upgrade/failover plan, disk placement and shared job limits. Add preload/restart only if the chosen extension design requires it. Avoid advertising a universal one-command installation.
4. **Prepare one authorized snapshot:** agree edge direction, weights, duplicates, isolates, string IDs and filters. Read in bounded batches, record the source watermark, build and validate the prepared generation. PostgreSQL being the source does not eliminate graph projection or ID-mapping work.
5. **Return one complete useful result:** preserve original IDs, algorithm/parameter/version metadata, completeness and authorization. Budget result serialization, database import and subsequent indexing. Run the same supported question with a new seed and then refreshed input.
6. **Verify ongoing operation:** installed version after update, session behavior, resource receipt, stale readers, crash cleanup, backup/restore and next-generation overlap. Reject unsupported deployment shapes before the customer invests in preparation.

For the external route, PostgreSQL supports `COPY ... TO STDOUT` and `FROM STDIN` over the client connection; server-filename/`PROGRAM` variants have different filesystem and privilege implications. Thus a client export/import path can avoid native library installation, but it still needs data privileges. `COPY FROM` into RLS-enabled tables has restrictions; select a tested insertion/staging path that preserves policy instead of bypassing it. [PG18 COPY](https://www.postgresql.org/docs/18/sql-copy.html)

## Whole-Host 4 GB Accounting

The following is an **inferred engineering acceptance model**, inherited from the local workflow, not a measured PostgreSQL configuration.

| Stage | Include in the same-machine measurement | What cannot be hidden |
| --- | --- | --- |
| Source/extraction | PostgreSQL source backends, buffers, concurrent baseline workload, export executor state, client buffers | The source DB is not free because the graph kernel is small. Remote source RAM is outside the worker host but inside total-system cost. |
| Dataset preparation | Parser, validation/error samples, ID maps, sort runs/merges, encoding, graph/index generation and publication | A larger remote graph builder invalidates a claim that this whole job completed on one 4 GB machine. |
| Query | Backend/runtime, Knight Bus state, PostgreSQL executor intermediates, foreign-library heaps, worker/thread stacks and buffers | A 3 GB allocation per session is not a shared 3 GB budget. `work_mem` does not reserve the remaining host capacity. |
| Output/import | Serialization, driver queues, slow-consumer buffering, result rows, indexes and import executor state | A low-memory kernel followed by client-side all-result materialization does not satisfy the workflow. |
| Refresh/operations | Old/new generations, pinned readers, autovacuum/maintenance overlap, telemetry and recovery | Measure simultaneous occupancy, not independent stage peaks. One heavy stage at a time is the initial proposed schedule. |

Use one authoritative host accounting view, with non-overlapping explanations for shared memory, resident mappings/page cache, private heaps and kernel overhead. Summed per-process RSS can double-count shared pages. Swapping or a container OOM kill does not demonstrate successful bounded completion. An OS/container limit is containment; completion requires admission, bounded algorithm state, adequate disk and workable deadlines.

**In-process:** include PostgreSQL and Knight Bus together. The inherited 1 GB reserve cannot simply be assumed to cover a running production database plus OS; measure and redivide it.

**Same-host sidecar:** separate process/allocator accounting is useful, but PostgreSQL plus the sidecar still must fit 4 GB together.

**Remote worker:** a 4 GB worker plus managed PostgreSQL is a two-system claim. Report source compute, export impact, egress, latency and result-write cost separately; do not call it a 4 GB total system.

**Disk:** count source retention, PostgreSQL tables/indexes/WAL, prepared blocks, staging, scratch, old/new overlap and output according to actual placement. Keep the 50 GB unique retained-prepared cap separate from peak live disk. Database result imports can add storage and write amplification; extension-owned files need explicit backup/retention handling.

**Two meanings of build:** compiling the OSS extension is distinct from preparing the customer's graph. Prebuilding release binaries elsewhere can be disclosed as software supply-chain work. It does not justify exporting the customer's graph to a larger hidden preparation machine. No 4 GB compiler-build claim was tested either.

## Why Popularity Does Not Equal Installable Audience

**Inference, not a market-size estimate:** the immediately reachable native-extension audience is the intersection of users with the matching graph job, compatible server/runtime, operator approval, native deployment rights or provider inclusion, and a workable lifecycle budget. PostgreSQL usage alone supplies none of the other conditions. Managed hosting can reduce a customer's ability to install software precisely because they delegated server operation to the provider.

The evidence cuts both ways. An extension can keep source access and result joins in the customer's SQL environment; a separate worker can avoid native server modification but introduces extraction and another executable to operate. Neither delivery choice eliminates preparation, refresh or output costs. Existing pgRouting/MADlib/AGE/GraphBLAS-class functions also mean the differentiator cannot be merely "graph algorithms callable from SQL." The 4 GB source-to-answer contract remains a proposed distinction requiring comparable end-to-end evidence.

Provider inclusion is also not permanent. The documented RDS PL/Rust removal and Supabase version-policy change demonstrate that provider-specific maintenance and upgrade behavior belongs in installation feasibility, not only in a later operations checklist. [RDS PL/Rust](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/PostgreSQL.Concepts.General.Using.PL_Rust.html), [Supabase policy](https://supabase.com/changelog/extension-version-pinning-ignored)

## Gaps and Source Access

## Key Findings and Exact Sources

1. **Technically feasible does not mean already safe or bounded.** pgrx provides the native Rust integration path; memory-context ownership, parallel restrictions and whole-host admission still need deliberate engineering. [pgrx](https://github.com/pgcentralfoundation/pgrx), [PG18 resource rules](https://www.postgresql.org/docs/18/runtime-config-resource.html), [parallel safety](https://www.postgresql.org/docs/18/parallel-safety.html)
2. **The native deployment gate is distinct from SQL privileges.** Standard RDS/Aurora, Neon and Supabase documentation provides curated-extension/TLE routes, not evidence that customers can upload arbitrary Knight Bus binaries. [RDS rules](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Appendix.PostgreSQL.CommonDBATasks.Extensions.html), [Aurora catalog](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraPostgreSQLReleaseNotes/AuroraPostgreSQL.Extensions.html), [Neon catalog](https://neon.com/docs/extensions/pg-extensions), [Supabase overview](https://supabase.com/docs/guides/database/extensions)
3. **Trusted is not one capability.** PostgreSQL trusted packaging, trusted languages, `pg_tle` and provider delegation solve different problems. RDS's removal of PL/Rust at PG18 makes older Rust-through-TLE advice particularly unsafe to generalize. [Extension controls](https://www.postgresql.org/docs/18/extend-extensions.html), [pg_tle](https://github.com/aws/pg_tle), [RDS PL/Rust](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/PostgreSQL.Concepts.General.Using.PL_Rust.html)
4. **Useful graph functionality already exists.** Evaluate the actual customer query against AGE, pgRouting, MADlib, OneSparse and recursive SQL; compare complete preparation/query/output costs rather than feature labels. [AGE MATCH](https://age.apache.org/age-manual/master/clauses/match.html), [pgRouting functions](https://docs.pgrouting.org/latest/en/), [MADlib graph modules](https://madlib.apache.org/docs/latest/group__grp__graph.html), [OneSparse algorithms](https://onesparse.com/test_examples_header.html), [recursive SQL](https://www.postgresql.org/docs/18/queries-with.html)
5. **External compute is a real alternative integration shape, not an in-process extension.** Client COPY can support extract/import without a Knight Bus native server module; count all local processes under 4 GB, or explicitly declare the remote-source/worker boundary. [COPY](https://www.postgresql.org/docs/18/sql-copy.html), [local lifecycle contract](/Users/amuldotexe/Desktop/personal-repos-lane/knight-bus-graph-walker/research_4gb_20260919/End-To-End-Workflow.md)
