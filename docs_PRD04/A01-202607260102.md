# PART 0 — The architecture decision: per-algorithm materialization

**"Based on the algorithm run, a new storage format is created. As simple as that."**

## 0.1 What this actually is

Not "a format." **Per-algorithm materialization on demand.** `Arch06.md` reached
the edge of this idea and stopped one step short:

> *"WCC wants: labels resident, edges streamed once per pass, tiles skippable when
> settled. LOUVAIN wants: capped tally maps, coarser levels as new tiny
> generations, hot/cold scratch split. PAGERANK wants: compressed re-scannable
> strata, delta-skippable tiles, warm-startable rank vector."*
>
> *"Three algorithms, three different residency/scratch/iteration designs."*

`Arch06` then split **substrate** (shared) from **plan** (bespoke). This decision
goes one step further: **skip the shared substrate; materialize the artifact.**

The consequence is that the entire Arch01–Arch06 "which format wins" question
**dissolves**. There is no universal format to argue about.

## 0.2 GRAIN's five rules, unbundled

"Forget GRAIN" sounds like discarding five design rules. It isn't — only two are
expensive, and they are the two that do not help our priority families:

```text
  G1  degree-ranked dense IDs      -> a sort at build time. NEARLY FREE.  KEEP
  G2  three strata, three codecs   -> Elias-Fano + 2D blocks. EXPENSIVE.  DROP
  G3  THE MANIFEST IS THE ESTIMATOR-> works over ANY layout.              KEEP
  G4  blocks are the spill unit    -> requires G2.           EXPENSIVE.   DROP
  G5  immutable generations        -> a directory + atomic rename. FREE.  KEEP
```

**G3 does not depend on G2.** The estimator — per `evidence01.md` the one
capability Slater, Grafeo and LadybugDB all lack — needs `|V|`, `|E|` and a degree
distribution, not strata.

## 0.3 What each artifact looks like

This is what makes the decision obviously right: each artifact is a weekend, not a
quarter, because each serves exactly one access pattern with no generality tax.

```text
WCC ARTIFACT
  file:      sorted (u32 src, u32 dst) pairs, one orientation, deduped
  resident:  parent u32[V]  = 0.745 GiB at 200M nodes   (PRD05 arithmetic)
  streamed:  the edge file, once per pass
  ESTIMATE:  4V bytes resident + 8E bytes read.  EXACT. No polynomial.

NODESIMILARITY ARTIFACT            <- a completely different thing, and that is fine
  file:      per-node adjacency SORTED ASCENDING (merge-intersection ready)
             + degree array
             + optional fixed-width MinHash sketch per node (Arch06 L1.c)
  resident:  top-K heaps + sketches -- both bounded BY CONSTRUCTION
  ESTIMATE:  K x V x entry_width + sketch_width x V.  EXACT.

PAGERANK ARTIFACT
  file:      reverse CSR + out-degree array
  resident:  2-3 x f32[V]  = 2.235 GiB at 200M
  streamed:  reverse CSR per iteration

TRIANGLE ARTIFACT
  file:      degree-ordered relabeled, only lower->higher edges
             (the standard triangle optimisation -- this is G1 paying rent)
```

## 0.4 The risk this retires — and it is the biggest unproven bet in the corpus

`Arch05`'s **X1 was the load-bearing unverified assumption of the whole
architecture**: *can NodeSimilarity and Louvain workspace be expressed as
closed-form polynomials over a universal manifest, within ±30%?* Its own
verification table graded it:

> *"V6 — Is the 'manifest polynomial' claim proven for the state-heavy families?
> **NO — it is the document's central creative bet.** … honest-uncertainty (the
> load-bearing one)."*

The experiment never ran. **Per-algorithm artifacts make the question disappear.**
You are not predicting workspace from a *universal* manifest — you built the
artifact *for this algorithm* and know its exact shape. The bill becomes arithmetic
over a structure you just wrote.

> **The estimator gets easier and more accurate, not harder.** That is a rare
> trade: the simplification strengthens the one differentiator we still hold.

## 0.5 The one thing this needs that the proposal did not state

You still need **one canonical intermediate**. Otherwise running four algorithms
means reading the customer's Neo4j four times — the export cliff, four times over,
with the extraction-load risk of §1B.2 multiplied.

```text
   Neo4j  --extract ONCE-->  BUILD STORE   --materialize on demand-->  WCC artifact
          (or from backup)   canonical,                                NodeSim artifact
                             never queried                             PageRank artifact
```

That is `prd-l1.md`'s **Projection Build Store**, and it turns out to be the one
part of the original PRD that survives every revision. Users never query it. It
exists so that extraction happens exactly once.

## 0.6 Why the corpus's rejection of this no longer applies

`Arch01` Option D (FOUNDRY — *"print several formats, pick per job"*) was killed
for **"3x build cost, 3x storage, parity-proving every copy."** Four things changed:

| Then | Now |
|---|---|
| Build all copies **always** | **Build on demand** — only what is actually run |
| Seven families | **Two** (WCC + NodeSim for ER) — 2 artifacts, not 7 |
| Storage on the production DB box | Storage on **our** OLAP box — a sizing decision, not an incident |
| Parity per copy = a burden | Parity per copy = **the differential harness PRD06 says is the actual product** |

Under the OLAP-only + identity scope, the multiplication risk is roughly **2×**, on
hardware we control.

## 0.7 What it costs — honestly

- **First run of any algorithm pays a build.** PRD05 requires this be reported as
  `T_first = T_prepare + T_execute`, compared symmetrically against GDS's own
  projection cost. Fair: GDS pays projection on *every* run; we pay it once per
  artifact.
- **Artifact lifecycle needs a policy** — keep, evict, or rebuild on refresh.
  Decide before the first customer, not after.
- **Disk grows per retained artifact.** Quote it in the receipt (§1.4). The PART 1
  band of 2–5× becomes roughly **2× per additional retained artifact** — which is
  why "build on demand, evict on policy" matters more than compression ever did.

## 0.8 What this deletes from the roadmap

```text
  DELETE:  Elias-Fano warm stratum      (Slater already shipped it, and it helps
                                         neither WCC nor NodeSimilarity)
  DELETE:  GridGraph 2D cold blocks
  DELETE:  the universal manifest polynomial, and Arch05 X1 with it
  DELETE:  the Arch01-06 "which format wins" question -- permanently

  KEEP:    degree-ranked IDs      (free; triangle counting wants it anyway)
  KEEP:    immutable generations + atomic publish  (a directory and a rename)
  KEEP:    the estimator          -- now EXACT per artifact rather than fitted

  ADD:     the Projection Build Store, so extraction happens exactly once
```

## 0.9 Why this is right for *this* scope specifically

`Arch05` rated flat/minimal formats at ~30% and killed them because *"cold-stratum
graphs 3–5x larger than RAM have no story"* — but that verdict was priced against
**seven families in an uncontested market**. Both premises have since changed:

```text
  WCC          0.745 GiB resident + streamed edges  -> FITS 8 GiB on plain layouts
  NodeSim      bounded by scratch, NOT by layout    -> Arch02 R2: "no static layout
                                                       of the ORIGINAL graph removes
                                                       that cost"
```

**GRAIN's strata are aimed at scan-heavy repeated-pass algorithms** (PageRank,
FastRP, triangles) — precisely the families this scope deprioritises. For WCC and
NodeSimilarity they contribute nothing.

**Net: a WCC artifact, a WCC kernel, an exact receipt, and an empty `diff` against
`gds.wcc.stream` are reachable in roughly two weeks** on the mmap runtime that
already exists — with none of the format work.

# PART 1 — Yes, the disk is affected. Three ways, and one of them can kill the pitch.

## 1.1 Space: 2–5× Neo4j alone (already priced in PRD05)

`docs_PRD05/Neo4j-Rust-Two-Scenario-Estimation.md` §"Disk, Build, And Freshness"
answered this before the question was asked:

| Dimension | Scenario A (resident rewrite) | **Scenario B (our read-shape architecture)** |
|---|---:|---:|
| Base OLTP store + indexes | roughly Neo4j-like | roughly Neo4j-like |
| OLAP topology | one resident projection, 6–20+ GiB | **16–20 GiB current dual CSR, or 3–12 GiB per compressed / orientation-specific view** |
| Generations retained | catalog-defined resident graphs | **at least old AND new during atomic publication** |
| Projection Build Store | optional staging | **10–50+ GiB depending on retained IR and compaction** |
| **Total disk vs Neo4j-only** | 1.0–1.6× | **2–5× typical planning band; higher with many hot views** |
| 50 GiB snapshot publication | 1–20 min | **5–45 min** with external sort, validation, multiple views |

Deterministic arithmetic, from the same document:

```text
  dual CSR total bytes = 8E + 36V + 16 + K

  at V = 200M nodes, E = 1B directed relationships:
     avg key  8 bytes -> 15.65 GiB
     avg key 16 bytes -> 17.14 GiB
     avg key 24 bytes -> 18.63 GiB

  single-orientation topology floor = 4E + 8(V+1) = 5.22 GiB
  (v002 measured: snapshot ~= 23.51% of raw generated CSV bytes)
```

PRD05's own adversarial pass already conceded the point — Duck 2:
*"Algorithm-shaped copies may consume more disk and build time. Response:
correct. Disk, publication lag, and generation count are explicit costs in
Draft 2."*

And the sentence to internalise before any external claim is made:

> **"Scenario B trades storage capacity and freshness for controlled runtime RAM.
> A marketing claim that omits this trade is incomplete."**

## 1.2 Wear (TBW): a non-issue — and this is genuinely good news

The instinct is that streaming from disk grinds the SSD. It does not, because
**flash wear comes from writes, not reads.**

```text
  READ-HEAVY -> NO WEAR
    every OLAP query, every mmap fault, every PageRank iteration.
    PRD05: strict 20-iteration PageRank = 20 x 5.22 GiB = 104.4 GiB of
    READ traffic per run. Costs IOPS and wall-clock. Costs ZERO endurance.

  WRITES -> REAL WEAR, BUT PERIODIC
    snapshot build, external-sort spill runs, generation publication.
    One 50 GiB-class build ~ 20-60 GiB written
    (snapshot + spill amplification; local builder uses external sorted runs
     with a 64 MiB logical budget and a one-quarter spill buffer).
```

A daily rebuild of a 50 GiB-class graph is roughly **20 TB written per year**.
Enterprise NVMe endurance is rated in **petabytes** written. Wear is two to three
orders of magnitude away from mattering.

Say this confidently when a DBA raises it. Note also that the incumbent has its
own costs here: GDS re-projects on every run, and `gds.graph.drop` does not
return memory to the OS, forcing restarts.

## 1.3 The real risk, which nobody in the corpus has named

This is the finding that matters, and it threatens rung **V1** of
`Win-The-Whales-Vision.md` directly.

```text
  THE PITCH:  "our analytics cannot touch your heap"

  THE HOLE:   we still share the DISK, the PAGE CACHE, and the IOPS budget
              with the production database.

      Neo4j OLTP  --reads-->  OS page cache  -->  same NVMe
      grain.*     --mmap -->  OS page cache  -->  same NVMe
                              ^^^^^^^^^^^^^
                        WE EVICT THEIR WORKING SET
```

Three failure modes, each of which looks to a DBA **exactly like the thing we
promised to prevent**:

1. **Page-cache eviction.** We mmap a 16 GiB snapshot; the OS evicts Neo4j's hot
   store pages to cache ours. Neo4j's p99 goes from 5 ms to 200 ms. We never
   touched the heap — and we still caused the incident.
   PRD05 Duck 6 states the mechanism plainly: *"mmap does not enforce an 8 GiB
   limit. It delegates residency to the operating system."*
   PRD05 Correction 5: *"Low process RSS is not low total machine RAM."*
2. **IOPS contention.** 104 GiB of streaming reads during a PageRank saturates the
   queue depth the WAL needs for fsync. Write latency spikes; transactions back up.
3. **Disk exhaustion.** DBAs provision database volumes tightly. Adding 2–5×
   storage without warning **fills the production disk** — a harder outage than an
   OOM, because Neo4j then cannot write its WAL at all.

> **This is blast radius wearing different clothes.** Moving harm from RAM to I/O
> and declaring victory would be the single most damaging thing we could ship,
> because it would burn the exact trust the plugin strategy depends on.

## 1.4 Mitigations — most already exist in the architecture

| Risk | Mitigation | Already in the corpus? |
|---|---|---|
| Page-cache eviction | **`O_DIRECT`** for the strict lane — bypasses page cache entirely | **Yes** — `Arch-options.md`: *"O_DIRECT + compio for strict file-data RAM control"*; *"mmap is fast mode; O_DIRECT is strict-RAM mode"* |
| Page-cache eviction | `madvise(MADV_DONTNEED)` / `POSIX_FADV_DONTNEED` after each pass | No — add |
| IOPS contention | cgroup v2 `io.max` throttle on the grain process; `ionice` | No — add |
| IOPS contention | Separate device / volume for snapshots (the clean deployment default) | No — recommend in the README |
| Disk exhaustion | **Pre-flight disk quote in the receipt**: refuse to build if free space < required | **Half** — the estimator exists for RAM; extend it to bytes-on-disk |
| Retained generations | Retention policy + GC of superseded generations | **Yes** — `Snapshot-Publication-State-Machine.md` |

The fifth row is the elegant one and should be built first:

```text
   CALL grain.snapshot.estimate('myGraph')
     -> { residentBytes, diskBytes, freeDiskBytes, buildScratchBytes, verdict }
     -> REFUSES to start if the disk cannot take it

   The manifest-as-estimator (Arch05 G3) already computes a RAM bill from ~1 KB
   of metadata. Make it quote DISK as well. Same insight, second resource --
   and it converts the biggest operational objection into a live demo of the
   core differentiator.
```

## 1.5 What to measure in the week-2 spike (free, and it is the real V1 proof)

Add to `grain.ping` / WCC parity at no extra cost:

```text
  While a grain run executes against a LIVE Neo4j, capture:

    - Neo4j p50 / p99 query latency        <- MUST STAY FLAT. This is the proof.
    - /proc/meminfo Cached; host page-cache pressure
    - major/minor page faults, blkio read/write bytes, for BOTH processes
    - free disk before/after build; peak scratch during external sort
    - Neo4j heap (must be flat -- necessary, NOT sufficient)
```

> "Heap flat" is necessary and insufficient. The claim that actually sells is
> **"your OLTP p99 did not move."** That is a measurement, not an argument — and
> if it moves, we learn it in week 2 rather than in a customer's incident review.

# PART 1B — The separate-OLAP-server variant

**"Take one snapshot of your Neo4j, once, then run it on a separate box."**

## 1B.0 Is it something that is done? Yes — it is the *dominant* pattern

This is not novel and should not be pitched as novel. It is the most established
architecture in data engineering, and — critically — **the incumbent's own newest
product is exactly this**.

| Precedent | What it is | Status |
|---|---|---|
| **Neo4j Aura Graph Analytics** (GA 2025-05-07) | Serverless, **zero-ETL**, pulls from *any* data source, runs 65+ algorithms in a **separate metered session**, writes back | **VERIFIED** (`evidence01.md`). *This is the incumbent shipping the exact architecture.* |
| **GDS graph projection itself** | A frozen in-heap copy at a watermark; users already accept staleness | Verified — `simulation01.md` |
| **Slater `slater-build`** | Offline compiler: Cypher dump → *"immutable, content-hashed generation directory"*, then N stateless servers serve it over Bolt | **VERIFIED** — a competitor shipping precisely this |
| **AWS Neptune Analytics** | Loads from S3/Neptune into a separate memory-provisioned analytics engine | Verified directionally |
| **The entire warehouse/lakehouse industry** | OLTP → ETL/CDC → separate analytical store (Snowflake, BigQuery, Databricks, medallion) | Universal |
| **Read replicas / backup-restore-to-analytics** | Standard DBA practice for decades | Universal |

> **So the answer to "is this done?" is: yes, overwhelmingly, including by Neo4j.**
> That cuts both ways, and the cut matters more than the reassurance.

**The strategic cost, stated bluntly.** `PMF03.md` BUG-1 already recorded this and
it applies with full force here:

```text
  PMF03 BUG-1 (SEVERITY: HIGH):
    "Part of our pitch is now their press release."

  IN-PROCESS PLUGIN          ->  UNCONTESTED GROUND
     nobody else can be inside a running Neo4j.
     Slater and Grafeo structurally cannot follow -- they ARE the
     replacement database.

  SEPARATE OLAP SERVER       ->  CROWDED GROUND
     you are now competing with Aura Graph Analytics (zero-ETL, serverless,
     the vendor's own product), Slater, Grafeo, LadybugDB, Neptune Analytics,
     and every warehouse. On maturity, support, references and risk --
     the six axes a database evaluation is decided on -- a new entrant
     loses all six.
```

Moving to a separate server trades our only defensible position for technical
comfort. That trade should be made consciously, not by default.

## 1B.1 What the variant DISSOLVES (this is real and substantial)

| Risk from PART 1 | Status on a separate server |
|---|---|
| **Page-cache eviction of Neo4j's working set** (§1.3, the biggest risk) | **GONE.** Different machine, different page cache. |
| **IOPS contention with WAL fsync** | **GONE** — except during the extraction window (see 1B.2). |
| **Filling the production disk** | **GONE.** Our 2–5× storage lands on our box. |
| **`dbms.security.procedures.unrestricted=grain.*`** — hostile ask in a bank | **GONE** if no plugin runs in prod. |
| **U1: plugin/GPL derivative-work question** (listed BLOCKING in `Everything-We-Know-Now.md`) | **LARGELY DISSOLVED.** No linking against Neo4j's kernel API in-process. Still needs counsel, but the hard question mostly evaporates. |
| **"Zero heap contact" is unmeasured** (U2) | **Becomes structurally true**, not a measurement claim. Far easier to sell: *"it is a different machine"* beats *"trust our memory accounting."* |

That is four risks removed and one blocking legal risk defanged. **This variant is
genuinely, materially safer.** It should not be dismissed.

## 1B.2 What it CREATES — nine new issues, ranked

### Issue 1 — The extraction step becomes the entire product risk ⚠️ **the big one**

The corpus has flagged this three separate times and never solved it:

```text
  Arch06 closing:  "weakest journey step is EXPORT from Neo4j
                    (2-8 hrs, 30-40% failure risk)"

  simulation01 P1: "Worked on the CSV dump. Now can it read my Neo4j store
                    directly?"     <- the simulated first user reaction
```

With a plugin, the export cliff was *inverted into the funnel* — the data was
already there. On a separate server, **the cliff comes back and stands between the
user and every single thing we do.** It is now the first thing they experience.

### Issue 2 — Extraction load: the risk MOVES, it does not vanish

Pulling 50 GiB out of a live Neo4j — via Bolt, APOC export, or a full scan — is
itself a large sequential read that pressures the very page cache and IOPS budget
we were protecting. **§1.3's risk is not eliminated; it is compressed into the
extraction window.** A 2–8 hour full scan against production is arguably *worse*
than a bounded mmap, because it is unthrottled and lasts hours.

> **The fix, and it is the best idea in this section: extract from the BACKUP,
> not from production.** Most enterprises already take nightly backups. Restoring
> an existing backup onto the analytics box and extracting there imposes
> **literally zero additional load on production**, and a backup is a *consistent
> point-in-time image*, which also solves Issue 3. This should be the documented
> default path.

### Issue 3 — Snapshot consistency (a correctness issue, not a performance one)

A multi-hour scan of a live database yields a **smeared, non-transactional view**:
node A read at 01:00, its relationship written at 02:00, node B read at 03:00.
Algorithms then run on a graph state that never actually existed. WCC components
can be wrong in ways no `diff` against a *later* GDS run will reproduce.

Options: `neo4j-admin database dump` (offline / requires stopping the DB), online
`backup` (Enterprise), or a consistent read snapshot. *(Specific Neo4j tooling
constraints here are general knowledge, not from this session's sources — verify
before relying on them.)* The backup path in Issue 2 resolves this cleanly.

### Issue 4 — Staleness becomes a product property, not a footnote

A **one-time** snapshot is frozen at watermark W forever. `prd-l1.md` accepts OLAP
lag and requires the watermark be reported — good — but note the buyer mismatch:
`simulation01.md` §13.2 identifies **fraud/AML as the deepest-pocketed segment and
explicitly "re-run-heavy"**, on a growing graph. A frozen snapshot serves a
one-shot analysis, not a daily fraud pipeline. Refresh strategy is therefore
mandatory, not optional: full rebuild, or CDC-driven incremental *(Neo4j CDC is
Enterprise-tier — general knowledge, verify)*.

### Issue 5 — Node-ID mapping, still the top source of silent wrongness

`gtm-POC-01.md` named this precisely: *"node-ID mapping (Neo4j internal ids vs
GRAIN dense ids) must be exact — this is the single most likely source of silent
wrongness."* Across a machine boundary this gets **harder**, because Neo4j internal
IDs are not stable across restarts, compactions, or restore-from-backup. You need
a stable business key or `elementId`, carried in a sidecar, and the parity harness
must prove the mapping — not assume it.

### Issue 6 — Data governance and egress: an enterprise-grade blocker

Copying the production graph to another machine is a **data-classification event**.
In regulated shops it triggers security review, possibly DLP, possibly a refusal.
Note the irony against our own positioning: `PMF03.md` re-aimed the whole pitch at
*"your hardware, your data"* precisely because Aura requires egress. A separate
server is a smaller version of the same objection — mitigated if the box is inside
their perimeter, fatal if it is ours.

### Issue 7 — The second box reintroduces the cost conversation

You now need hardware. This is defensible — the pitch becomes *"a 16 GiB analytics
box instead of a 512 GiB database"* — but it is no longer free, and it re-opens the
procurement conversation the plugin avoided entirely.

### Issue 8 — Write-back across a network boundary

`gds.*.write` semantics mean results land back in Neo4j. In-process that is a local
call; across a boundary it is a bulk load with its own transaction, failure, and
idempotency story. `gtm-POC-01.md` deliberately scoped write-back **out** of POC-1
("stream + the user's own SET clause covers the demo") — that scoping is even more
important here.

### Issue 9 — You become a server, not a jar

Deployment, monitoring, upgrades, security patching, HA, auth. The plugin's
killer property — *"delete the jar and nothing changed"* — is lost. Reversibility
drops from **total** to **ordinary**.

## 1B.3 Disk, restated for this topology

Good news: the numbers get *better*, because the costs relocate to a machine you
control and size deliberately.

```text
  ON THE PRODUCTION NEO4J BOX
    +0 GiB steady state          <- nothing installed, nothing stored
    transient read load ONLY during extraction (and 0 if you use the backup)

  ON THE OLAP BOX
    snapshot        15.65-18.63 GiB   (dual CSR at 200M/1B, PRD05 formula)
                    or 3-12 GiB per compressed / orientation-specific view
    build scratch   external sort runs + spill
    generations     old + new during publication
    Build Store     10-50+ GiB if retained IR is kept
    ----------------------------------------------------------------
    plan for 3-5x the logical graph size on a dedicated volume

  WEAR: unchanged and still a non-issue -- reads dominate, writes are periodic.
```

The 2–5× multiplier does not go away. It **moves onto our box**, where it is a
sizing decision instead of an incident.

## 1B.4 The resolution: extract in-process, execute out-of-process

The two options are not exclusive, and the hybrid keeps the strategic asset while
taking the technical safety:

```text
  +-------------------------------------------+     +-------------------------+
  |  PRODUCTION NEO4J (untouched, stock)      |     |   OLAP BOX (ours)       |
  |                                           |     |                         |
  |  grain-export.jar   <- TINY. extraction   |     |  full Rust OLAP runtime |
  |   CALL grain.snapshot.build(...)          |     |  7 algorithm families   |
  |   - streams (src,dst) + keys out          |---->|  admission control      |
  |   - NO algorithms, NO heap projection     |     |  receipts, generations  |
  |   - bounded, throttled, resumable         |     |  16 GiB box             |
  |   - or: skip entirely, read the BACKUP    |     |                         |
  +-------------------------------------------+     +-------------------------+
           ^                                                     |
           |                    results stream back (optional)   |
           +-----------------------------------------------------+

  WHY THIS IS THE ANSWER:
   - keeps the ONE-LINE adoption path inside Neo4j  (the uncontested asset)
   - kills the export cliff -- the #1 documented adoption blocker
   - heavy execution is isolated: no page-cache eviction, no IOPS war
   - the plugin stays tiny -> licensing exposure is minimal, and
     page-cache impact is bounded to a throttled extraction window
   - reversibility survives: delete the jar, delete the box
```

**The extraction plugin is the wedge. The separate server is the engine.** The
strategic asset was never "our algorithms run in your process" — it was *"getting
started costs you one line."* That property is preserved by a 200-line exporter and
does not require the OLAP runtime to live in production at all.

## 1B.5 What this changes in the risk register

| Risk | Before | After (hybrid) |
|---|---|---|
| U1 plugin licensing | **BLOCKING** | **Much reduced** — a thin exporter is a far smaller surface than an in-process algorithm engine. Still ask counsel. |
| U2 "zero heap contact" unmeasured | **BLOCKING** | **Reduced** — structurally true for execution; still measure the extraction window. |
| Page-cache / IOPS (§1.3) | **Unnamed, severe** | **Contained** to a throttled, resumable extraction — or **eliminated** by reading the backup. |
| Export cliff | Solved by the plugin | **Solved, and it stays solved** — this is why the exporter must remain in-process. |
| Strategic position | Uncontested | **Preserved** — adoption path still starts inside Neo4j. |
| Staleness / refresh | Implicit | **Now explicit and mandatory** — design the refresh story before the first customer asks. |

# PART 2 — The career question. Yes, and it is arguably the stronger reason.

## 2.1 What is actually being learned (not "graph algorithms")

That framing undersells it badly. Ranked by **market scarcity**:

| Skill | Scarcity | Transfers to |
|---|---|---|
| **Storage engine internals** — CSR, mmap vs `O_DIRECT`, external sort, WAL, page cache, immutable generations / MVCC, atomic publication | **Very high** | Every database company on earth |
| **Differential / oracle testing at scale** — PRD06's convergence thesis: harness as the product, equivalence definitions, canonicalization | **Very high, badly underrated** | Any compatibility or migration engineering — Postgres-/MySQL-/S3-compatible systems. A large, boring, extremely well-paid category |
| **Out-of-core / external-memory algorithms** — GraphChi → GridGraph lineage, spill, admission control | High | DB internals, ML infra, anything memory-bound |
| **Memory accounting as engineering** — holistic RSS + page cache + scratch, closed-form estimators | High | Systems and platform roles; FinOps-adjacent |
| **Rust systems programming** with real concurrency and unsafe boundaries | Medium-high, rising | Broad |
| **Graph algorithms at systems level** (implementing the 7 families, not calling them) | Medium | Graph DBs, fraud/AML, GraphRAG |
| **Wire-protocol compatibility** (Bolt / PackStream) | Medium | Protocol and driver work |

> The first two rows are the career assets. **The graph algorithms are the least
> valuable item on the list** — a semester of study, and commoditized. The storage
> engine and the verification harness are what companies genuinely cannot hire for.

PRD06 sharpens this further, and it is the most career-relevant sentence in the
whole repo:

> *"The generated Rust is a regenerable artifact. The coverage of the differential
> harness is the asset — it is the compressed form of the endpoint."*

Under the AI regime, code generation is 10–50× faster but **semantic archaeology
and verification are only 2–3× faster**. The scarce skill is therefore precisely
the one this project forces you to build: knowing what "correct" means and being
able to prove it mechanically.

## 2.3 The honest risk: illegibility, not irrelevance

The failure mode is **not** "these skills don't matter." It is:

> One year on a private repo nobody used, described as *"rewrote Neo4j in Rust"*,
> which a hiring manager reads as **overreach** rather than **depth**.

Depth becomes career capital only when it is **legible and verifiable**. A private
27-document corpus is worth approximately zero in an interview.

`The-One-Question-Left.md` §9 framed **Path B** — contribute the admission/receipt

> Two independent lines of reasoning — strategic and career — now converge on the
> same action. That convergence is worth more than either argument alone.

## 2.5 The asymmetry that makes the year rational

```text
  P(the business succeeds hugely)        ~0.15
      (The-One-Question-Left.md §6)

  P(the skills transfer if it fails)     ~0.90
      storage engines and differential testing do not expire;
      they get scarcer every year
```

That is a rare and genuinely good asymmetry. Most failed startup years leave a
dead CRUD app and domain knowledge nobody wants. **This one leaves database-
internals depth in a market where Apple buys teams for it.**

**One condition, and it is not negotiable:** the skills accrue only if you are
**compiling**. Fourteen weeks produced 27 documents, 7,423 lines of Rust and —
per PRD05's own audit — **zero implemented GDS algorithm kernels**
(`Implemented GDS algorithm kernels: 0`). A year of documents teaches nothing a
hiring manager can test. A year of shipped, benchmarked, differentially-verified
Rust makes you genuinely hard to replace.

## 2.6 SCOPE REVISION — the career answer if we build **OLAP only**

*Added 2026-07-26.* Revised premise: **no OLTP database at all.** Storage is
delegated (CozoDB or similar), ingestion is via connectors, the OLAP engine is the
wedge and the whole product, and the primary application is **online identity
processing** (entity resolution).

**Direct answer to "that's slightly narrower, right?" — it is narrower on one axis,
wider on two, and net it is career-POSITIVE.** Here is the accounting.

### 2.6.1 What you give up (and why losing it is a gift)

```text
  DROPPED WITH OLTP:
    WAL and group commit          lock managers and deadlock detection
    crash recovery correctness    transaction isolation / MVCC for writes
    durability and fsync policy   record store + page cache for writes
```

Prestigious work. Also: **the hardest, least-forgiving, least-transferable half of
a database**, valued by maybe twenty employers worldwide, and — per PRD05 — the
half that turns the project into a 3–6 year, 12–25 engineer program.

`simulation01.md` §7.8 already reached this conclusion strategically: OLTP
slowness is a high-volume complaint we **explicitly do not fix**, and being
*"loudly OLAP-only"* is a **credibility asset**. This scope decision therefore
aligns strategy and career simultaneously — the third time in this analysis that
two independent axes converge on the same choice.

### 2.6.2 What survives — more than the framing suggests

Delegating the *transactional* store to CozoDB does **not** remove storage
engineering. You still build the entire analytical storage layer yourself:

```text
  STILL YOURS, STILL DEEP STORAGE WORK:
    CSR / dual-CSR layout            Elias-Fano and compression codecs
    mmap vs O_DIRECT residency       external sort with a memory budget
    immutable generation catalog     columnar property sidecars
    atomic publication + rollback    degree-ranked ID assignment
    holistic memory accounting       admission control and spill
```

That is the `Arch05` GRAIN work in full. **The storage-engine credential largely
survives; only the transactional half is gone.**

### 2.6.3 What you gain — two additions, both larger markets than what you dropped

**(a) Analytical execution engine skills.** OLAP-only pushes you into
vectorised/pull-based operator pipelines, spill-aware execution, pipeline
breakers, cost-based planning over access plans. `docs_PRD06/graph-learning/`
already contains the pattern notes for this (`pull-operator-pipeline`,
`posting-block-compression`, `roaring-bitmap-idsets`, `semiring-matrix-traversal`).

> **This is the DataFusion / Velox / DuckDB / ClickHouse / Polars / Arrow lane —
> and it is a substantially larger and faster-growing job market than OLTP storage
> engines.** Every lakehouse, query engine and vector database is hiring for it.
> OLTP storage-engine roles are rarer and concentrated in fewer companies.

**(b) Entity resolution as a paid domain.** "Online identity processing" is not a
generic application — it is a lucrative vertical with dedicated companies, and it
maps *exactly* onto the highest-weight algorithm families you were already going to
build:

```text
  simulation01 §13.1:  "WCC -- the workhorse of ENTITY RESOLUTION: build a
                        similarity graph over records (shared email, device,
                        address) and every connected component is one
                        real-world entity."

  Arch02 adoption weights:   WCC ~20%   +   NodeSimilarity/KNN ~12%
                             = the two families identity processing needs most
```

So the narrowed product scope lets you go **deep on precisely the two families
that carry the most adoption weight**, and honestly decline the rest.

### 2.6.4 Who hires, under the revised scope

The Tier-1/2/3 list in §2.2 still holds. **These are additions specific to
OLAP-only + identity** *(company names here are general knowledge, not from this
session's sources — verify before relying on them)*:

```text
  ANALYTICAL ENGINE LANE (grew; now your primary market)
    DuckDB Labs / MotherDuck, ClickHouse, Databricks (Photon), Meta (Velox),
    InfluxData, Polars, Apache DataFusion ecosystem, StarRocks, Firebolt,
    vector DBs (Qdrant, LanceDB, Weaviate) -- all fighting the SAME fight:
    bounded memory, spill, columnar layout, out-of-core execution.

  ENTITY-RESOLUTION / IDENTITY LANE (new, and it pays well)
    Graph-native ER:     Quantexa (graph-based KYC/AML ER -- the closest
                         commercial analogue to what you would build),
                         Palantir, Senzing, Zingg, Splink (UK-gov OSS)
    Fraud / identity:    Socure, Sardine, Unit21, Feedzai, Featurespace
    Identity graphs:     LiveRamp, TransUnion/Neustar, Experian, Acxiom,
                         Amperity, Zeta Global
    In-house:            every bank's AML/KYC function; every marketplace's
                         trust-and-safety team
```

### 2.6.5 The honest downsides of the narrower scope

| Risk | Assessment |
|---|---|
| **"I built an analytics engine" is a weaker soundbite than "I built a database"** | True — but it is **far more credible from a solo builder** and far more verifiable. An unfinished database reads as overreach; a finished, benchmarked, differentially-verified analytics engine reads as depth. Net positive. |
| **Connectors can eat the year and teach nothing** | **The real danger.** Integration work is necessary, unbounded, and does not differentiate on a CV. **Guard rail: two or three connectors, treated explicitly as commodity.** If connector work exceeds ~15% of engineering time, the scope has drifted. |
| **CozoDB dependency reduces depth on transactional storage** | Accepted deliberately. You lose WAL/recovery/locking depth. You keep all analytical storage depth (§2.6.2). This is the trade you *want*. |
| **ER domain knowledge is vertical-locked** | Partly. Hedge is structural: the **engine** skills are horizontal and portable; the **ER domain** is a bonus vertical, not the foundation. Do not let the CV become "identity person who can code." |

### 2.6.6 The revised one-line career answer

```text
  BEFORE (full rewrite):   storage engines + verification harness + graph algos,
                           spread across BOTH halves of a database, with the
                           OLTP half likely unfinished after a year.

  AFTER  (OLAP-only):      analytical execution engines + analytical storage
                           + verification harness + entity resolution,
                           ALL of it finishable, in a LARGER job market,
                           with a paid vertical attached.

  NARROWER IN SURFACE. WIDER IN MARKET. DEEPER PER UNIT TIME.
  And -- decisively -- FINISHABLE, which is the only condition under which
  any of the skills actually accrue (see 2.5).
```

The asymmetry from §2.5 improves under this scope: `P(skills transfer if the
business fails)` rises from ~0.90 toward ~0.95, because analytical execution and
out-of-core algorithms are *more* transferable than transactional storage, and
because a narrower scope is far likelier to produce **shipped, benchmarked
artifacts** — which is the condition on which the whole career argument rests.

## 3. All three answers in one sentence each

**Disk.** It **is** affected — 2–5× space, negligible wear, and a real
page-cache/IOPS contention risk that must be **measured in week 2 and quoted in
the receipt**, or it will silently break the exact promise we are selling.

**Separate OLAP server.** It is **absolutely a done thing** — so established that
Neo4j's own Aura Graph Analytics *is* it — and it **dissolves the page-cache risk
and most of the blocking licensing risk**, at the price of resurrecting the export
cliff, adding staleness, and **surrendering the only uncontested position we
have**; the resolution is a **hybrid: a tiny in-process exporter as the wedge, a
separate box as the engine.**

**Career.** The year **is** worth it, but only in its public form, which happens to
be the same form the strategy already pointed to.

## 4. Actions this generates

```text
  [ ] ADOPT PER-ALGORITHM MATERIALIZATION (PART 0). One artifact per algorithm,
      built on demand from a canonical Build Store. Delete Elias-Fano, delete
      2D blocks, delete the universal manifest polynomial and Arch05 X1.
      KEEP degree-ranked IDs, generations, and the estimator -- which becomes
      EXACT per artifact instead of a fitted polynomial.

  [ ] BUILD THE PROJECTION BUILD STORE FIRST-ish -- it is the one thing PART 0
      needs that the proposal did not state. Extract from Neo4j ONCE; every
      artifact is materialized from it. Without this, N algorithms = N exports.

  [ ] DECIDE THE ARTIFACT LIFECYCLE POLICY (keep / evict / rebuild-on-refresh)
      before the first customer. Disk grows ~2x per retained artifact, so the
      policy matters more than compression ever would have.

  [ ] NAME THE UNIT OF THE PRODUCT and hold the line on it:
          (one algorithm) x (one query shape) x (one refresh cadence)
      "WCC @ hourly" and "Louvain @ weekly" are TWO INDEPENDENT PRODUCTS that
      happen to read the same Build Store. Each gets its own artifact, receipt,
      window and budget. BUILD COSTS ARE NEVER SUMMED ACROSS UNITS.
      This is PART 0's "build ON DEMAND -- only what is actually run" restated
      as a product rule, and it is the retired failure mode of Arch01 Option D
      ("3x build cost, 3x storage") that summing would reintroduce.
      Corpus evidence for one-at-a-time: EVERY complaint we hold is about a
      SINGLE algorithm (52 GiB clustering, 130 GiB NodeSimilarity, 5-hour
      Louvain, shortestPath OOM). Not one is about a multi-algorithm sweep.
      GDS ergonomics are one CALL per procedure; Aura Graph Analytics is a
      per-workload SESSION with a 10-minute floor.

  [ ] SIZE THE BUILD PER UNIT, NEVER AS A SWEEP. The question is "does WCC's
      build fit WCC's cadence?", not "does everything fit in an hour?".
      Expect ~5-15 min for WCC-precompute on a 50 GiB graph.

  [ ] FIX T_OPEN -- we currently LOSE to Neo4j (189.979 ms vs 90.446 ms, v002).
      No amount of precomputation touches it, and for frequent small queries
      T_open IS the latency. Try lazy manifest validation instead of the full
      offsets + node-record + key-index scan on open.

  [ ] PRECOMPUTE THE QUERY, NOT JUST THE ALGORITHM. Knowing "PageRank" buys a
      0.8 GiB score array; knowing "PageRank, top 100" buys a 4 KB sorted list
      AND removes the 6-30 s serialization tail that would otherwise hide the
      entire compute win. Knowing the QUERY is worth more than knowing the
      ALGORITHM.

  [ ] ADOPT THE HYBRID as the reference topology: tiny in-process
      grain-export.jar (extraction ONLY, no algorithms) + separate OLAP box.
      Keeps the one-line adoption path; isolates the heavy execution.

  [ ] MAKE "EXTRACT FROM THE BACKUP" THE DOCUMENTED DEFAULT PATH.
      Zero additional production load, and a consistent point-in-time image
      that also solves the smeared-snapshot correctness problem.

  [ ] DESIGN THE REFRESH STORY BEFORE THE FIRST CUSTOMER ASKS.
      A one-time snapshot does not serve fraud/AML, which simulation01 §13.2
      identifies as re-run-heavy AND deepest-pocketed. Full rebuild cadence
      or CDC-driven incremental -- decide and write it down.

  [ ] PROVE THE ID MAPPING, do not assume it. Neo4j internal IDs are not
      stable across restart/compaction/restore. Use a stable key or elementId
      in a sidecar; the parity harness must verify the mapping itself.
      (gtm-POC-01: "the single most likely source of silent wrongness")

  [ ] Extend the estimator to quote DISK, not just RAM:
      grain.snapshot.estimate -> {residentBytes, diskBytes, freeDiskBytes, verdict}
      and REFUSE to build when the disk cannot take it.

  [ ] Add to the week-2 spike: Neo4j p50/p99 during EXTRACTION (the risk now
      lives there, not in execution), page-cache pressure, blkio for both
      processes, free disk delta.

  [ ] Throttle and make the exporter RESUMABLE. A 2-8 hour scan with a
      30-40% failure rate is the documented #1 adoption blocker; resumability
      is the difference between a demo and a product.

  [ ] Re-ask counsel about U1 under the HYBRID: a thin exporter is a far
      smaller derivative-work surface than an in-process algorithm engine.

  [ ] Publish, from day one: benchmark artifact bundles, the estimator spec,
      the plugin. Private work has no career value.

  [ ] Evaluate contributing the admission/receipt layer to Slater (Apache-2.0)
      -- dominant on BOTH the strategy axis and the career axis.
```
