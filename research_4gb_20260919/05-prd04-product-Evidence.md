### Product Contract

The desired outcome is **a useful correct answer before its decision expires, at a deployment cost the owner accepts, followed by a trustworthy next answer after data changes**. A refusal without damage is a reliability success; if it refuses the important jobs, it is not product success. A checksum is an integrity aid, not proof that source extraction or an authorization rule was correct. A post-run resource receipt is diagnostic evidence, not automatically an audit-control certification or purchase motive.

Ask each prospective owner for the most recent affected job, dated input, output used, workaround and consequence. Then establish:

- **Freshness:** maximum age at answer completion, source-commit versus export-cutoff meaning, and whether deletions/revocations have a stricter deadline than insertions. Can a stale snapshot be used for exploratory investigation but never enforcement?
- **Reuse:** useful queries per generation and per index/projection; how often seeds, edge types, node filters, weights, personalization, dimension and k change. Count abandoned and refused queries too. Ask what gets reused after each refresh, not only whether the algorithm name repeats.
- **First answer:** time from customer-accessible CSV or authorized Neo4j source to the first decision-ready result. Record collection/export, validation, ID mapping, build, seal/open, queue, execution, serialization and consumer processing separately. An attractive first row is not a complete negative finding.
- **Money and ownership:** what can actually be retired or downsized; who retains the Neo4j license/source host; worker and source storage/I/O/network costs; review, patching, backups, on-call and failed-run recovery. A customer able to buy RAM can still dislike its cost, but the actual purchase trigger must be observed.
- **Commitment:** a scrubbed artifact plus change trace, oracle reviewer, agreed acceptance window and scheduled adoption decision. Five interviews can guide the next experiment; they cannot establish population size or prove a segment empty.

Use the original lifecycle equations without weakening their boundaries:

```text
Physical peak = worker group + colocated source + OS/other unshared memory <= 4,000,000,000
Prepared peak = unique retained graph/index/dictionary/result blocks across generations <= 50,000,000,000
Total disk peak = prepared + raw staging + unsealed builds + scratch + spools + logs/checkpoints
Answer age = answer completion - source consistency watermark
Per-horizon cost = retained source + extraction/interference + worker
                   + storage/I/O/transfer + integration/ops/recovery
```

No double-counting shared pages or build compute; no omission of reclaimable file cache from physical pressure. The 50 GB prepared cap is not a raw-input-size promise. Temporary space is separately admitted and measured, not silently assumed unlimited; retained generations and persistent accelerators consume the prepared cap. When source is remote, four-billion-byte worker fit must be labeled worker-only and accompanied by the source's cost and load. When source is colocated, both must fit the same machine. Migration-to-smaller-instance savings count only after the instance or bill actually changes.

For horizon planning, let the extra full preparation/holding/refresh cost be A and per-use realized saving for compatible query i be s_i. Reuse pays back only if `sum(s_i) > A` before invalidation, with freshness and first-answer constraints also met. Changes in algorithm parameters can invalidate only some accelerators but not others; their reuse must be counted separately. This is why a fixed-query benchmark cannot select a physical design for a known family with unknown future queries.

### Architecture Refinements

These refine original H1-H4; they are hypotheses using established techniques, not additional claims of global originality.

**H1a, first-answer-aware preparation.** Test a fully validated minimum reusable base with exact bounded scan/spill execution before building optional reverse, sorted-property or specialized candidate planes. Publish each accelerator only against the same graph/mapping identity. Choose additional preparation using observed reuse and refresh liability. This can reduce first usable answer time while a later batch earns faster queries. It may lose badly when the first query needs random reverse access or a full scan takes too long. Never call an incomplete source import a complete graph: absence/negative results require complete coverage of all eligible adjacency and predicates, not just the rows seen so far.

**H2a, versioned output contracts.** Separate endpoint-set/count exploration, one explicit witness and complete requested shortest-path output as distinct APIs/contracts. Retain only proven-valid results/certificates for the exact contract and generation. Customer preview requests justify progressive output only with clear completeness and continuation semantics, not silent replacement of paths by nodes or bags by sets. A shortest-path predecessor choice, stable relationship identity, equal-distance ties and filtered alternatives need separate proof; original endpoint-cache correctness does not provide it. Test result-consumer memory and review utility alongside kernel cost.

**H1b, lifecycle admission across deployments.** Reserve memory, prepared bytes, scratch and source scan capacity for build/refresh as well as queries. Compare a source-exporter plus isolated worker with an external exporter and an embedded component; do not assume a plugin wins procurement. Commit a generation only after source consistency and semantic checks; stop or degrade optional accelerator work before it delays mandatory freshness. An admission estimate can have conservative byte bounds while runtime remains a measured range. A hard cap must not be sold as a guarantee of completion by a fixed deadline.

H1a/H1b may be more valuable than a novel traversal kernel if build/refresh dominate. They may also be unnecessary complexity when a straightforward immutable CSR plus bounded sorting meets the user's complete workflow. The experiment must be allowed to select that simpler design or an existing engine.
