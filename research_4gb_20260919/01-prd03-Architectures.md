# PRD03: Five Resource-Accounted Architecture Hypotheses

Updated: 2026-09-20. Status: **research hypotheses, no implementation or performance results**. Assigned reading is complete: 150 nonempty documents fully read and 19 empty artifacts inspected, with exact spans and observations in [the evidence ledger](01-prd03-Evidence.md). These five mechanisms were drafted during reading and remain hypotheses, not claims of global originality. Other lanes may contain related proposals; cross-corpus comparison remains an integration task.

## Recommendation And Product Boundary

Start with an offline analytical companion for an existing Neo4j user who repeatedly rebuilds a projection to inspect dependencies or compute a small set of analytical outputs. The useful promise to test is: finish a named exact job, from extraction through export, on a 4,000,000,000-byte host with declared disk and freshness costs. It is not "replace every Neo4j/GDS procedure" or "fit arbitrary graphs in RAM."

Three candidate jobs are filtered dependency traversal, a bounded source cohort's unweighted Jaccard neighbors, and batch PageRank with an explicit completion deadline. Refresh reuse is useful when transactional updates frequently touch columns irrelevant to the analytical projection. These buyer/workload choices are **product hypotheses**, not interviews or demand evidence established by this lane. Transaction-heavy Cypher/APOC applications, arbitrary path enumeration, large dense embeddings and freshness-critical OLTP remain poor initial fits.

Compare against real GDS projections and algorithms as well as Neo4j Cypher. Compressed GDS adjacency is the incumbent baseline. Compare against a simple external-CSR implementation too, so engineering complexity must earn its cost. A user switching from Neo4j must still pay for extraction, ID mapping, refresh lag, result import, operational tooling and unsupported procedures.

## Prior Art And Novelty Boundary

The repository already proposes CSR, external sorting, typed sidecars, immutable generations, reservations, spilling, cells, artifact catalogs and support tiers. Merely combining these names is not an innovation.

- [GraphChi, OSDI 2012](https://www.usenix.org/conference/osdi12/technical-sessions/presentation/kyrola), abstract read: single-PC disk graph computation and evolving graphs are established prior art, not a new market-independent technical discovery.
- [X-Stream implementation README](https://github.com/bindsch/x-stream), rendered lines 173-219 read: edge streaming, partitions, explicit buffers and direct I/O already exist, including a warning that page-cache access can suit smaller graphs better. We do not infer GDS semantic parity from its PageRank example.
- [Scaling Up All Pairs Similarity Search, WWW 2007](https://research.google.com/pubs/archive/32781.pdf), abstract/introduction through problem statement, rendered lines 0-85 read: exact indexed similarity search and disk-resident extensions predate this proposal. Its full proof and disk algorithm have not been reviewed in this lane.
- [Differential Dataflow, CIDR 2013](https://www.microsoft.com/en-us/research/?p=163907), publication abstract read: incremental iterative computation is established. H4 deliberately addresses the narrower no-semantic-change certificate, not a new general dynamic-graph algorithm.

The proposed deltas are the specific contracts and resource schedules below. Their value is conditional on tests against simpler incumbents. The available evidence does not establish patent novelty or superiority.

## Common Accounting

Let `P=4,000,000,000` physical bytes and provisional workload allowance `W=3,000,000,000`; reserve `R=1,000,000,000` for OS and other uncharged costs. This reserve is an assumption to validate. A live local Neo4j extractor, benchmark client, builder and worker must share the same machine allowance, not each receive W. An offline-export mode may stop Neo4j before building; a remote-export mode must disclose remote compute and transfer costs.

Define `N` selected nodes, `E` stored directed adjacency entries after orientation/multiplicity rules, `p` relationship property columns, `d_max` maximum stored degree, `U` distinct external keys, `V` bytes in an intermediate sort stream, `k` merge fan-in, and `b` its per-run input buffer. Count undirected expansion, self-loops, types and inverse indexes explicitly. `E` is not necessarily source relationship count.

`M_peak = max_t [M_anon(t) + M_file_charged(t) + M_kernel_charged(t)] <= W`.

The anonymous term includes live algorithm arrays, allocator overhead, worker stacks, codec buffers, queues, clients and build buffers. Its subcomponents are a planning decomposition, not extra additions to RSS. Mapped file bytes are not necessarily resident bytes, and mapped RSS is not added again to charged file cache. Sum simultaneous jobs; use a maximum only when lifetimes provably do not overlap.

For verification use an isolated host/VM configured at no more than P bytes, no swap, and a workload cgroup below P, with high-water and event counters plus whole-host observations. The [Linux cgroup v2 memory documentation](https://cdn.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html) tracks major anonymous, file-cache and kernel uses, but explicitly does not promise perfectly watertight accounting; limits may be page-rounded and transiently exceeded. Therefore `memory.max` is a safety net, not proof of useful completion or an exact instantaneous physical bound. Keep margin and reject any observed OOM, swap or unexplained accounting discrepancy. These controls have not been run on this macOS workspace.

Persistent preparation and peak disk are different quantities:

`D_peak = D_local_input + D_retained_graphs + D_build_staging + D_sort_runs + D_ID_join_runs + D_receipts_WAL + D_result_spools + D_job_checkpoints + D_retry_overlap`.

The research scenario permits a **50,000,000,000-byte prepared persistent graph**, not a 50 GB input or free unlimited scratch. Assign a separate actual free-disk/quota bound to D_peak before admitting a job. Until input/key/property distributions are supplied, no universal build-disk number is defensible. Retention includes readers, rollback and model/result references. Safe cleanup can reduce overlap but cannot delete pinned generations.

For uncompressed 32-bit peers with 64-bit offsets, one direction costs `8(N+1)+4E` disk bytes; dual direction costs `16(N+1)+8E`, before maps, types, labels, values and indexes. At `N=200,000,000`, `E=1,000,000,000`, this is approximately 11.2 GB. One 64-bit external-ID column adds 1.6 GB; variable string keys need their actual encoded lengths, offsets and lookup index. A 64-bit peer representation doubles the peer term. A dual representation of one f64 edge weight adds another 16 GB at that E unless a different indirection layout is explicitly priced.

Compare fairly with GDS: its inspected varlong store has approximately `12N + compressed_targets + page overhead` for one direction/type, not one object per edge. Our opportunity is bounded residency/build lifetimes, not CSR discovery. Compression can also be used in our plan, but decode buffers, directory pages and random-access costs still count.

### Lifecycle Schedule

| Phase | RAM, disk and I/O obligations | Correctness and recovery obligation |
| --- | --- | --- |
| Extract and validate | Bounded transport batches and row decoding; local input or durable receipts consume disk. Input width requires streaming decode or an explicit supported maximum before allocation. | Transaction-consistent source watermark; include isolated nodes. Validate types, null/default semantics, relationships and projection filters. Source data may change during extraction. |
| Map IDs | External unique-key sort plus endpoint merge joins; dictionary/index and joins are separate from edge sorting. Sparse high source IDs must not force a high-water-sized dense allocation. | Preserve original IDs, writeback mapping and any original-ID-based random seeds. Unknown endpoints follow projection-mode semantics, not silent dropping. |
| Build | For a bounded merge, require `k*b + heap(k)*head_record_bytes + decode + output + overhead <= B_sort`. Fan-in is capped; total run count is not. | Preserve duplicate policy, property alignment, direction and stable aggregation semantics. Full result changes cannot be hidden by deduplication. |
| Seal and validate | Write graph/sidecars, checksum and scan them; keep previous generation while staging is live. | Counts/checksums prove structural integrity, not algorithm parity. Validate topology/property associations and bounds before publication. |
| Publish and query | Pin generation before reading; charge all query state, cold faults, result spools and simultaneous builders. | Lookup/pin must interlock with GC. Durable manifest/pointer ordering and restart behavior require crash tests. |
| Export or write | Result production, network serialization, client buffering and actual Neo4j writeback all count. | Stream/mutate/write are distinct. A file link is not a compatible replacement for a GDS result list or database write. |
| Refresh and retry | Old plus new graph/state, change log, retained results, sort runs and retry remnants can coexist. | Detect commit-before-receipt gaps; recover from authoritative logs or stop. Do not publish a watermark across a missing interval. Resume verified runs or discard only unreferenced staging. |

If initial run capacity is `B_run`, `r=ceil(V/B_run)`, `h=ceil(log_k r)`, one fixed-width external sort approximately reads/writes `2V(1+h)` bytes, plus any original extraction, final index emission and validation not fused into those passes. Peak sort disk is roughly old plus new runs, up to about `2V`, under a deletion/recovery policy; it is not all historical passes added together. ID mapping and reverse-direction sorting can each add separate sorts/joins. Compression, variable-width records and comparison costs invalidate a byte-only CPU estimate. Persist counts and measured phase I/O, not just this model.

## H1: Degree-Independent Projection Compilation

**Problem and evidence.** The inspected GDS `DeltaVarLongCompressor.java:218-228` allocates a property-sorting matrix proportional to `p*d_max`. A single hub can therefore defeat an otherwise small final encoding. The current Knight Bus pattern already spills global runs, but its run fan-in and oversize-record admission require tightening.

**Mechanism.** Externally order complete relationship tuples by projection partition, source, target and a retained duplicate-order key. Fuse the final merge with segmented adjacency emission. A logical neighbor cursor spans bounded compressed chunks for a hub, with bounded restart-index buffers. Emit aligned property chunks from the same ordered tuple stream, not a full in-memory property permutation for the whole row. Keep dense row directories disk-resident with a bounded directory cache; do not require 12N resident directory bytes.

**Increment over consumed sources.** The falsifiable contribution is a compiler/cursor contract whose peak scratch is independent of maximum degree, while preserving the projection's duplicate and property semantics. External sorting, CSR segmentation and varints are prior techniques, not new inventions.

**Resources.** For C concurrent encoders, `M_build <= B_extract + B_map + B_sort + C*(B_edge_chunk + p*B_value_chunk) + B_directory_cache + B_metadata + charged_cache/kernel`. Choose C from the same permit pool as queries. The replaced hub term is approximately `8*p*d_max` temporary property bytes in the inspected path; this is not a whole-GDS estimate. Disk adds segment headers/restarts and bounded-sort runs; construction I/O is the common sort model. A typed wide value must itself be streamed or rejected before allocation. If a codec requires a whole row, it is ineligible for this plan.

**Correctness.** Cursor concatenation must expose the same logical adjacency and property pairing as the pinned oracle. `NONE` preserves multiplicity; `SINGLE`, `COUNT`, `SUM`, `MIN`, `MAX`, missing defaults and NaN follow their actual loader rules. Stable ordinals preserve chosen reduction order, but the upstream order must first be traced. Floating SUM cannot be assumed associative. UNDIRECTED/self-loop and inverse-index validation stay intact. Publication happens only after all segments and schemas validate.

**Refresh/output/failure.** Rebuild changed chunks and their indexes only if ID stability and sorted boundaries permit it; otherwise use a fully accounted rebuild. Sealed output is the graph, not a lossy degree-capped variant. Adversaries: one enormous property value; duplicates with cancellation-sensitive floating sums; random IDs that compress poorly; low-degree graphs where header cost dominates; disk exhaustion while old readers pin the previous graph.

**Experiment before implementation promotion.** Specify a hub family at fixed E with increasing `d_max` and p, including duplicate/self-loop/NaN fixtures. Compare decoded topology and properties to pinned GDS projection. Instrument live allocations and verify scratch slope in `d_max` is zero once chunk limits are reached. Compare build wall time and D_peak against plain external CSR. Reject H1 if scratch still grows with degree or the segment overhead makes the target jobs slower without enabling larger completed jobs.

## H2: Logical-Order Traversal With Physical-Order Reads

**Problem and evidence.** Local traversal is promising for dependency exploration, but random cold reads and GDS order/termination semantics conflict. GDS BFS returns a visited-node list and traversal path, not just a reached set; mutate forms a directed line graph in visitation order. Targets and depth affect stopping. [Official BFS documentation](https://neo4j.com/docs/graph-data-science/current/algorithms/bfs/), rendered lines 189-228 and 349-411 read. Pin the exact release before compatibility tests.

**Mechanism.** Tag adjacency requests with logical expansion tickets `(frontier_ordinal, neighbor_ordinal)`. For at most K pending edge entries, group fetches by physical page, decode with a bounded cache, then commit discoveries in ticket order. Speculative reads never commit visits, terminate early or mutate results. Spill the FIFO frontier and ordered results when necessary; backpressure at K prevents an unbounded reorder queue. A full row can be consumed over multiple windows.

**Increment.** The proposed test is whether a bounded lookahead can reduce page fetches while preserving ordered first-discovery and exact target stopping. Generic batched reads and external BFS are prior art; a reached-set-only optimization is insufficient for this contract.

**Resources.** `M_query <= ceil(N/8) visited + K*ticket_bytes + B_decode + B_page_cache + B_frontier + B_output + B_filter + overhead`. A source-to-target parent tree, if separately requested, adds its real state; it is not the GDS visitation line path. At N=200M, a visited bitset is 25 MB, but one 64-bit visited-ID result list can be 1.6 GB. Path/entity serialization adds more. The frontier and ID spool each cost up to `8N` disk bytes before representation overhead. I/O is fetched page bytes plus sequential frontier/result traffic, with potential rereads when the lookahead window is too small. Do not equate touched edges with physical bytes read.

**Correctness/scope.** Initially target unweighted, fixed-orientation BFS with explicit label/type filters and pinned traversal order. This does not solve weighted shortest paths or arbitrary Cypher path enumeration. Freeze projection ordering first; if upstream permits multiple orders, define the accepted equivalence rather than inventing one. Stop at the same target ticket and depth; never append nodes discovered speculatively after that point.

**Refresh/output/failure.** Queries pin one graph generation. H4 may avoid unnecessary refresh rebuilds, but cannot change a live query's graph. A compatible large single list/path requires a genuinely incremental compatible encoder or an admitted materialization budget; this remains an ABI engineering gap. An alternative paginated artifact API must be named as a changed product contract. Adversaries: tiny early target with wasted prefetch, adversarial page layout, dense frontier, giant requested path and cache competition from a simultaneous builder.

**Experiment.** Exhaustively compare small directed graphs with cycles, self-loops, duplicate edges, multiple targets, excluded intermediate labels and depth 0/1/2. Assert ordered IDs and synthetic path, not just membership. Then compare K=1, bounded lookahead and simple mmap under cold/warm caches with identical results. Reject the extra scheduler if it cannot improve cold target workloads at equal peak RAM, or if p95 regresses unacceptably on small early-termination queries.

## H3: Budgeted Exact Jaccard With Pruning Certificates

**Problem and scope.** Find a small source cohort's top-k similar entities from neighborhood sets without holding all candidate pairs or silently discarding hubs. First scope: unweighted set Jaccard on a verified simple projected neighborhood, fixed source/target eligibility, nonempty sets, topK and a similarity cutoff. Weighted metrics, bottomK/bottomN, global topN, distribution stats and arbitrary multigraph interpretation require separate contracts. GDS exposes these distinctions, so this is not a claim to implement the entire similarity family. [Official Node Similarity reference](https://neo4j.com/docs/graph-data-science/current/algorithms/node-similarity/).

**Mechanism.** Store degree-ordered candidate blocks and sorted neighbor streams. For source degree a and candidate degree d, `J <= min(a,d)/max(a,d)`. For a block with degrees `[l,u]`, the bound is 1 if a is inside that interval, `a/l` if a<l, and `u/a` if a>u. Skip a block only when its upper bound is strictly below the operative cutoff. Otherwise perform exact streaming intersections and retain a k-entry heap per active source. Record block interval, threshold and skip decision in a compact verification trace, optionally sampled in production but complete in tests.

**Proof boundary.** Intersection cannot exceed `min(a,d)` and union is at least `max(a,d)`, giving the bound. Threshold is the requested cutoff until k valid results exist, then also the kth score. Strict `<` preserves possible equal-score ties; apply the pinned tie rule. Floating threshold comparisons need conservative rounding or integer/rational comparison, never an under-rounded upper bound. Completeness comes from enumerating every eligible candidate block; an inverted index may optimize later only with its own completeness proof.

**Increment.** Degree/prefix bounds and exact all-pairs pruning are established. The hypothesis is that per-source bounded heaps, external intersections, conservative block certificates and admission based on output size form a useful small-host execution plan. It must beat the simple exhaustive external baseline on the intended degree distributions.

**Resources.** With s active source tasks, `M <= s*(k*result_entry_bytes + 2*B_neighbor + B_candidate_meta) + B_index_cache + overhead`. A hub's complete list is never mandatory in RAM. An on-disk `(degree,id)` index is approximately `16*N_candidates` bytes with 64-bit fields, built by a priced external sort. Worst-case work remains quadratic in candidate count and proportional to all intersected list lengths. Skips do not create a worst-case speed guarantee.

**Output and refresh.** For `N_sources` sources, directed output can approach `N_sources*k` records. With a 24-byte `(source,target,score)` record, 200M sources and k=10 already imply 48 GB before framing; that output cannot share a 50 GB workspace with an 11.2 GB graph. A cohort of 10,000 sources at k=10 has only 2.4 MB of such records. Restricting the cohort is an explicit job selection, not approximation. Changed neighborhoods invalidate their degrees and candidate bounds; because eligibility/ranking can change globally, do not reuse old top-k results merely because one source's own neighbors are unchanged.

**Failure and experiment.** Equal-degree near-cliques defeat the degree bound, and tie-heavy zero/one scores can defeat pruning. Very long lists cause expensive repeated disk scans. Build small exhaustive set fixtures, compare every permitted result and tie to GDS, and replay every skipped block with brute force. Include filter intersections, cutoff equality and hub cases. A prune false negative rejects the plan. A skewed-degree benefit must survive index build and refresh cost; otherwise keep the simpler external intersections.

## H4: No-Change Certificates For Projection And Result Reuse

**Problem.** Full projection rebuilds after changes to unused transactional properties can dominate useful work. Existing generation catalogs and cells discuss safe publication/local rebuild, but do not establish a precise no-semantic-change witness for reusing analytical outputs across watermarks.

**Mechanism.** At projection compile time derive a dependency contract covering node membership, relationship membership/direction/multiplicity, selected property values, missing/default distinctions, schema, original-ID mapping, configuration, algorithm version and any authorization inputs. For a complete contiguous receipt interval, prove that no mutation can change these dependencies. Publish a new metadata generation referencing the same immutable blocks and, for deterministic computations, the same result bytes with new provenance. Arbitrary opaque Cypher predicates, time-dependent defaults and incomplete receipts disable this shortcut.

**Correctness.** Under a sound dependency contract and complete change interval, projected logical input is unchanged. A deterministic algorithm with unchanged seed/version/config therefore has unchanged mathematical input/output. Absence is a dependency: adding the first matching edge or property must invalidate. Generation-local dense IDs must remain identical or undergo a separately verified mapping; stable original IDs alone do not prove byte-order compatibility. Do not reuse runtime timing/progress statistics as though computation ran again. Hash identity alone is not a semantic proof; use immutable block identity plus the change contract, with integrity checks separately.

**Increment.** This is a restricted, auditable reuse rule layered on the existing generation protocol, not a novel incremental-computation theory. Its advantage hypothesis is lower refresh amplification without maintaining a large general dynamic-graph state. It does not update PageRank after a topology change, nor top-k after candidate changes.

**Resources.** For bounded receipt batch size q, `M_refresh <= q*receipt_bytes + B_dependency_cache + B_catalog + B_publish + overhead`. Disk adds receipts, dependency metadata, result provenance and pinned manifests; unchanged shared graph/result bytes are counted once. With D changed dependency tokens and K projections, a naive check is `O(D*K)`; a disk-resident inverted dependency index trades maintenance/storage for postings scanned. High fanout can still touch all K. Receipt retention continues until every necessary consumer advances, so lagging consumers need a disk quota/backpressure policy.

**Refresh, failure and export.** Uncertain validation falls back to H1/full rebuild with old/new overlap. Commit-before-receipt gaps cannot advance the certificate. Interlock catalog resolve/pin with block GC, including crashes. A bookmark requiring transaction T can be satisfied analytically only after the complete interval through T is either rebuilt or certified irrelevant; a stale generation label cannot simply be renamed fresh. Reused results still incur client/export/writeback costs, and a new database write has its own transaction semantics.

**Experiment.** Generate mutations including unused property edits, first matching labels/edges, deletions, ID reuse, default-to-explicit changes, NaN changes, seed/version changes, missing receipts and revoked access. Compare every reused result to a clean rebuild. Add a crash between receipt, certificate and publication. One false reuse rejects the design. Require a materially lower end-to-end refresh time and bytes written on a workload whose irrelevant-change fraction is measured; if most changes affect topology, H4 has little product value.

## H5: Single-Resident-Vector Delta PageRank

**Problem and evidence.** Two f64 vectors for 200M vertices already cost 3.2 GB before graph or buffers. The inspected historical `PageRankComputation.java:60-109` does delta-message accumulation with per-node tolerance, not a freely substitutable normalized Jacobi formula. The challenge is retaining that recurrence while moving rank/checkpoint lifetimes to disk.

**Mechanism hypothesis.** Keep only the previous superstep's per-node outgoing contribution vector resident. Traverse incoming adjacency in destination order, reading source contributions from this vector, applying edge weights and reducing messages in the pinned permitted order. Stream the old rank and degree/weight-normalizer columns by destination; produce new rank and next contributions in bounded destination slabs on disk. Seal a manifest for the paired outputs at the superstep barrier, then load the next contribution vector over the old resident vector. Track active/send state separately when zero, underflow or halted-node semantics make a zero value ambiguous.

**Resources.** `M <= 8N contribution + B_destination_slabs + B_IO + B_active + B_catalog + overhead + charged_file/kernel`. With N=200M, the resident vector is 1.6 GB, leaving 1.4 GB of W for everything else; this is a feasibility calculation, not a measured fit. If the vector does not fit, fall back to an explicitly priced fully external scatter/gather plan, not hidden paging. Two durable rank and two durable contribution generations require up to `32N` bytes, plus active state and normalization columns. They coexist with graph generations and result export until reclamation is safe.

With f64 rank and normalizer columns, a simple non-fused iteration reads incoming adjacency, old rank and normalizers; writes new rank/contributions; then reloads contributions: approximately `S_in + 40N` bytes, plus flags and metadata. Unweighted degree derivation or fused reload can reduce this only when implemented and measured. For the 200M/1B unweighted example, `S_in ~= 5.6 GB`, hence roughly 13.6 GB/round or 408 GB for 30 rounds. An assumed sustained mixed sequential bandwidth of 500 MB/s alone gives about 816 seconds of I/O service; this is **not a latency prediction** and excludes compute, random DRAM access, extraction/build and failures.

**Increment and correctness gates.** Semi-external graph execution is established. The incremental hypothesis is an explicit column-liveness schedule for the pinned GDS delta contract, with crash-safe superstep artifacts rather than two resident full vectors. Before calling it compatible, trace the injected degree function, Pregel activation/termination, scaler and output mode. Personalized initialization, dangling nodes, parallel-edge weights, strict `delta > tolerance`, iteration counts and cancellation must match. Mathematical recurrence equivalence alone does not prove floating-point or stopping parity; incoming reduction order may differ from the original message reducer. Start with concurrency 1 and an explicitly pinned oracle; reject or revise the schedule on threshold-sensitive discrepancies.

**Refresh/output/failure.** H4 may reuse a completed result only when logical inputs are unchanged. Any relevant change triggers a fresh computation unless a separate dynamic algorithm is verified. Export the rank column as scalar rows; mutate publishes a result property, write performs actual database writes. A partial superstep is never a committed final result. Dense graphs, many unconverged rounds, weak SSD bandwidth or contraction/embedding workloads outside PageRank can make the plan useless despite fitting RAM.

**Experiment.** First compare every superstep rank, outgoing contribution, active status and final iteration count on tiny weighted/personalized/dangling/tolerance-edge fixtures. Then test increasing N at fixed degree, measuring resident slope near one f64 vector, complete disk traffic and wall time. Compare against ordinary two-vector external CSR where it fits, and compressed GDS. Kill H5 if semantics diverge or the intended overnight/batch deadline cannot be met. Never present bounded memory alone as success.

## Verification-First Sequence

1. Pin Neo4j, GDS, JVM, projection mode, concurrency, native worker, hardware and OS versions. Read remaining relevant source contracts before implementation. Correct the dossier rounding/routing errors in downstream test plans, without modifying shared source documents in this lane.
2. Write oracle fixtures before kernels: distinguish topology, ordered traversal, partition-label equivalence, numeric tolerance, convergence, side effects and output ABI. Include failed projection cleanup, catalog ambiguity and transaction/writeback failure.
3. Prototype H1's degree-bound contract first, then H2 for a narrow useful traversal job. H3 follows for a declared source cohort; H4 requires complete receipt semantics. H5 is a separate higher-I/O experiment, not a prerequisite for shipping every other workload.
4. Run at physical P with no swap. Include extraction/ID mapping/build/validation/publication/query/export/refresh/recovery and concurrent pin/build probes. Cold and warm runs must report actual page/I/O behavior. Sweep key length, property width, skew, duplicate ratio, filter selectivity, result size, mutation rate and retained generations.
5. Report admission rate **and useful completed jobs**, peak charged/host RAM, D_prepared and D_peak separately, total I/O, phase times, p50/p95 interactive latency, batch completion time, freshness lag and restart recovery. Record rejections and timeouts, not only successful runs.
6. Pre-register workload-specific targets before timing. Initial decision hypotheses: H2 must improve cold traversal p95 without semantic loss or >10% warm regression; H4 should reduce bytes written and refresh time by at least 2x on a declared mostly-irrelevant-update workload; H5 must meet the customer's batch window including preparation. These are proposed gates, not observed benefits, and need customer validation.

Do not promote any mechanism on metadata receipts alone. A sound memory plan can still be slow; a fast incomplete answer can still be wrong; a correct tiny fixture can still omit output or refresh amplification.

## Post-Coverage Workflow Review

Supplementary integration input: [End-To-End-Workflow.md](End-To-End-Workflow.md), fully read in contiguous spans 1-130, 131-225 and 226-298. This is outside the frozen 169-document denominator. The observations below refine the existing hypotheses, not add new architectures or measured claims.

1. **Source export is a product boundary.** Start with versioned node and relationship CSVs plus a projection manifest, including isolated nodes, external IDs, defaults and multiplicity. Bounded client batches do not establish bounded source-query execution: export-side sorting/materialization and a live local Neo4j process must enter the same 4 GB budget. The source snapshot mechanism remains a verification gate; a watermark label alone cannot make separately changing scans consistent. Remote extraction must disclose source resources and egress, while local offline export trades availability for a simpler serial budget.
2. **Bound the compiler before promising a 50 GB artifact.** Admit ID mapping, capped-fan-in sort, row decoding, hub compression and validation from one pool: `M_build = M_map + M_sort + M_decode + M_encode + M_output + M_cache/kernel + overhead`. Prove buffer lifetimes rather than summing independent phase maxima. One oversized record or the inspected `8*p*d_max` property scratch can break a naive spill plan. If the 50 GB prepared allowance includes retained answers as the workflow proposes, charge those inside it; peak disk still separately includes input, old/new generations, scratch and retries.
3. **Same GDS BFS ABI needs a delivery proof.** Preserve ordered visited IDs, traversal-order synthetic path, target/depth stopping, original-ID mapping and requested fields. The synthetic line path is not a source-to-target witness tree. A 200M-node visited-ID list alone is 1.6 GB at eight bytes per ID; bounded traversal does not bound encoder or client materialization. Either demonstrate compatible incremental encoding and a bounded receiving client or admit the complete required materialization. A paginated artifact or witness-only API is a different explicitly named product, not transparent GDS parity.
4. **Parameter changes need re-admission, not automatic rebuilding.** Classify each request against a versioned artifact capability manifest after config preprocessing/defaults. Supported BFS seeds/depth/targets can reuse topology but change frontier/output budgets. PageRank damping or tolerance can reuse an appropriate layout but invalidates stored answers and reruns computation. Filters, direction or new weights may need a new projection/index if the prepared artifact omitted necessary data. Estimate from the normalized config, model version and requested output; missing estimates are unknown, not zero. For sequential feature steps, charge `max_i(live_prior_outputs_i + scratch_i + new_output_i)`, not merely the largest isolated step.
5. **First answer must be useful and correctly named.** Track source-to-first-complete-answer separately from warm execution and first serialized byte. The serial reference is `T_export + T_validate + T_build + T_publish + T_queue + T_query + T_delivery`; overlaps require an actual schedule. A positive reachability witness may answer an explicit witness query early, but a negative search needs completion, and the full BFS ABI is not satisfied by that witness. Global top-k must be final or accompanied by a valid exclusion proof before it is presented as the answer.
6. **Refresh needs a second successful customer run.** Use immutable snapshots initially; relevant changes trigger a priced rebuild/recompute, and H4 reuse requires a complete change interval plus unchanged semantic dependencies. Refresh must re-admit old-reader pins, new preparation, prior answers and retries, with freshness measured from the source watermark. Two fully distinct 50 GB generations already require 100 GB before scratch. Deleting the only valid generation to fit is an availability change, not free optimization. Verify failed refresh preserves the old valid answer and never relabels stale data as current.
