## Rewrite Strategy Analysis — Shreyas Doshi Lens

*Analysis date: 2026-05-25*

Based on: `Neo4j-Architecture-Map.md`, `neo4j-loc-results.md`, and this journal.

### The Core Tension

The LOC numbers tell the story:

- **Cypher: 701,841 LOC (44% of Neo4j)**
- Storage + Kernel + IO + Index + WAL: ~197K LOC combined
- Knight Bus already replaces the storage layer with CSR arrays + mmap

Cypher IS Neo4j's product for most users. It's the reason people adopt Neo4j
over raw graph libraries. But it's also 44% of the codebase, mostly Scala
(512K LOC), and it's the layer that introduces most of the overhead Knight Bus
eliminates.

**The paradox: the thing that drives adoption is the thing that kills performance.**

### Three Strategies, Ranked by Adoption

#### Strategy A: No Cypher — Pure API (what Knight Bus does today)

- Ship fast, keep speed advantage, tiny codebase.
- **Adoption ceiling: very low.** Only appeals to users willing to rewrite all
  their queries as Rust function calls.
- *"You built a faster engine but removed the steering wheel."*

#### Strategy B: Full Cypher Rewrite in Rust

- 700K LOC to rewrite. Years of work, enormous surface area.
- Re-introduces the overhead we're eliminating (planner, pipe runtime,
  materialization).
- This is the trap of "feature parity" — we'll always be behind Neo4j on
  Cypher completeness.

#### Strategy C: Cypher-Compatible Subset — THE HIGH-LEVERAGE MOVE ✦

Support the ~20% of Cypher syntax that covers ~80% of real queries.

**What to include:**

- `MATCH` (fixed-hop patterns: 1-hop, 2-hop, variable up to N)
- `WHERE` (property filters, existence checks)
- `RETURN` (projection, `count()`, `collect()`, basic aggregation)
- `ORDER BY`, `LIMIT`, `SKIP`
- `UNWIND` (list expansion)
- Parameter binding (`$param`)

**What to skip:**

- `CREATE`, `MERGE`, `DELETE`, `SET` — immutable snapshots, no mutations
- `CALL` procedures / APOC — plugin ecosystem, unbounded scope
- Complex subqueries, `FOREACH`, pattern comprehensions
- `LOAD CSV` — use the existing build pipeline instead
- Full GQL/openCypher spec compliance

**Estimated scope:** ~15-25K LOC in Rust (parser + compiled query plan), not 700K.

**The pitch to users:** *"Drop in your existing MATCH queries. Same syntax,
100x faster, fraction of the RAM."*

### Can Both Variants Support Cypher?

#### variant_low_latency — YES, natural fit

- Parse Cypher once → compile to a native traversal plan → execute directly
  against CSR arrays.
- No interpreted pipes, no slot machines — the "query plan" becomes a sequence
  of array slices.
- The compiled plan is essentially what Knight Bus already does, just triggered
  by Cypher text instead of a function call.
- Memory cost of the parser/planner is negligible compared to the graph data.
- **This is where Cypher adds the most adoption value with the least
  performance cost.**

#### variant_low_RAM — CONDITIONALLY, with a different approach

A full in-memory planner is antithetical to the low-RAM goal. Options:

1. **Ahead-of-time compilation** — parse Cypher at build/config time, emit a
   static query plan that runs with zero planner overhead at runtime.
2. **Thin query DSL** (not Cypher) — a simpler syntax like
   `walk forward from KEY hop 2` that maps directly to CSR operations with
   near-zero parsing overhead.
3. **Pre-registered query templates** — allow only pre-compiled query templates
   that are compiled once and reused. No ad-hoc Cypher at runtime.

Options 1 or 3 preserve the Cypher compatibility story for adoption ("yes, we
support Cypher") while respecting the RAM constraint.

### Recommended Phased Approach

| Phase | What | Why | LOC estimate |
|---|---|---|---|
| 1 | Read-only Cypher subset parser | "Drop-in your MATCH queries" — removes biggest adoption barrier | ~8-12K |
| 2 | Compiled query plans for variant_low_latency | Cypher text → native CSR operations, zero interpretation overhead | ~5-8K |
| 3 | Ahead-of-time query compiler for variant_low_RAM | Parse at build time, execute at runtime with zero planner memory | ~3-5K |
| 4 | Bolt protocol (basic) | Existing Neo4j drivers work out of the box — language-agnostic access | ~5-10K |

**Total: ~20-35K LOC in Rust** vs Neo4j's 1.58M. A 98% reduction in codebase
size while capturing the adoption-critical surface area.

your MATCH statements."*
