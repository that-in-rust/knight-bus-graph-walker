### Parameterized Accounting

Use physical machine cap `P = 4,000,000,000` bytes and prepared-artifact cap `D = 50,000,000,000` bytes. Neither is the old hypothetical 50GB GDS projected-RAM scenario. Let `O` be the measured OS/other-process reserve, `C` concurrent workers, `V/E` admitted logical counts, `I` raw input bytes, `K` durable ID-map bytes, `F` required properties/features, `A` built topology, `X` retained results, `H` retained history/receipts, and `S` temporary working disk.

- Physical peak: `O + max_t(unique resident pages and allocations of builder + daemon + workers + verifier + exporters at t) <= P`. Measure file-backed resident pages, not virtual mapped length. Do not add heap to RSS or the same cache pages twice. Per-worker and per-stage caps compose by simultaneous lifetime, not by their labels. A provisional 1GB reserve would leave 3GB for all workload processes, not 4GB for each.
- Prepared disk: `A + K + F + indexes + manifests + X + H <= D` for everything retained as prepared product state. Report external exports separately but count them on the same volume if stored there. Calling something a sidecar, cache or receipt does not exempt it.
- Working disk: record `max_t(input retained + old pinned artifacts + new artifacts + sort runs + spool + WAL/checkpoints + exports + verifier scratch)`. If the machine's total volume is also 50GB, this whole expression must fit 50GB; a 50GB steady prepared artifact alone leaves no room for refresh. If workspace is separate, disclose its additional required capacity.
- Time to first complete verified answer: acquisition + parse/validation + ID mapping + sorting/layout/index/feature build + publication + cold query + all requested materialization/export + verification. Report first row separately. Allow overlap only where dependency-safe and actually measured; take wall time rather than summing overlapping timings.
- Refresh: change discovery + new-ID/property validation + delta normalization + changed layout/state computation + output reconstruction/export + verification + activation + later reclamation. Include concurrent old queries and slow exporters holding generation pins. Backlog must drain faster than arrivals; capped memory can otherwise produce unbounded lag/disk or perpetual refusal.

Illustrative arithmetic, not measured capacity: with `V=200,000,000`, `E=1,000,000,000`, 64-bit offsets and 32-bit destinations, one plain CSR is `8(V+1)+4E = 5,600,000,008` bytes on disk. Two orientations total 11,200,000,016 bytes before keys/properties. Two f64 vertex vectors alone are 3,200,000,000 bytes, already larger than a provisional 3GB workload budget; paging or a different valid state representation is necessary. A scalar export with an 8-byte ID and 8-byte value is 3.2GB binary, excluding text expansion. Ten 16-byte destination/score pairs per source are 32GB without source IDs/offsets. A 128-dimensional f32 matrix is 102.4GB and cannot be a fully retained 50GB prepared artifact. No kernel schedule resolves that disk contradiction without changing storage/retention/output requirements.

### Import And Refresh Gates

CSV needs byte-limited decoding, explicit maximum or streaming handling of oversized fields, duplicate/multiedge policy, isolated vertices, signed/variable-width IDs, nulls, weight domain, labels/types and temporal predicates. Neo4j extraction needs one consistent source snapshot/watermark or a declared reconciliation protocol across node/edge/property streams. Exporter fetch batches and any co-resident Neo4j process count toward physical RAM. Endpoint references, raw rows and logical orientation counts are distinct, exactly as the final negative fixture demonstrates (25463-25477).

ID normalization and exact degree/percentile probes may need external sorting before the main build. If normalized tuples occupy `L` bytes, run memory is `B`, and merge fan-in is `f`, initial runs are approximately `ceil(L/B)` and merge levels `ceil(log_f(ceil(L/B)))` when more than one run exists. Charge tuple width, input decode, output maps, all read/write passes, merge buffers and old/new run overlap. This is a planning expression, not a time prediction or automatic bounded implementation.

An update can change incoming messages without changing a local partition's bytes (24298). A topology/feature cache key must cover all semantic inputs, including filtering, weights, ID mapping, algorithm configuration and source version. Rebuilding an index must not silently change floating order, ties or seeded randomness. Deletion-aware refresh cannot be inferred from a seeded WCC merge fixture. A slow reader can retain more than two generations; use a pin/retention bound with explicit admission or refusal.

### Verification-First Experiments

These are scoped hypotheses and proposed experiments, not newly invented algorithms or measured wins.

1. **External scalar-vector workflow.** CSV and consistent Neo4j extraction feed a bounded sort/build, topology sidecars and WCC or a precisely specified PageRank profile; export typed scalar rows with original IDs, then refresh and re-export. Test whether topology reuse plus explicit state paging gives a useful completed-job envelope. Falsifiers: large V exceeds mandatory state/cache budget; random parent accesses dominate WCC; dense PageRank touches all state each iteration; first-answer build and export outweigh repeated-run savings. Compare against compact GDS state, not pointer objects.
2. **Exact blockwise score export.** Fix a known metric, candidate universe, self exclusion, duplicate handling and deterministic tie order. Maintain online global top-k per source block rather than retaining k candidates from every key block (21556-21562). Price input vectors, score tile, merge state, source blocks, full output and changed-vector refresh. Falsifiers: O(V squared) comparisons remain, output exceeds 50GB, or a single changed candidate alters many source top-k rows. This is not sampled-GDS-KNN parity merely because the columns match.
3. **Eligibility-checked endpoint queries.** Evaluate bounded endpoint/frontier-to-aggregation plans only where path/relationship variables and downstream multiplicities permit pruning (24477-24489). Price import, anchor index, frontier dedup, group keys/distinct sets, sorting, results and index refresh. A diamond gives two paths but one reached endpoint; cycles, min-depth constraints and path-dependent predicates defeat a universal reached-set rewrite. Compare legal specialized plans against Neo4j's existing pruning plans, not its ineligible path-materializing plan.
4. **Lifecycle-aware state/cache selection.** Under the same byte cap, compare simple degree/frequency caching and sequential streaming against a probe-selected cache/layout, including probe/reorder/build/warmup and refresh invalidation. Price queue depth, aligned IO, current/next windows and final flush. Falsifiers: workload shifts, no reuse, random accesses, full-dense iterative traffic, or oracle trace construction dominates savings. GPU-specific results remain outside a CPU-only claim unless that hardware is explicitly part of the experiment.

For every experiment include a tiny semantic oracle, skewed and sparse-ID fixtures, slow/disconnected exporters, injected build/flush/activation failures, a cold first answer, repeated-query sweep, and refresh overlap. Run the verifier under a separately counted cap, record full result coverage and divergent examples, and keep inconclusive verification distinct from success. No speedup or feasibility threshold is established until the entire workflow completes within both declared resources and the user's latency/freshness requirement.
