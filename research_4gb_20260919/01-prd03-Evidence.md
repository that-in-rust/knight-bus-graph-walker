## Findings So Far

1. Readiness is documentation readiness, not runtime readiness. The packet reports 1,232 `NeedsSource` cells and 17 `NeedsBenchmark` items (implementation-readiness README:104-126). These are historical reported counts, not freshly measured implementation coverage.
2. The support registry contradicts a literal reading of its own status vocabulary: PageRank/BFS rows are called `P1-ImplementedExactLowRam` while still containing `NeedsSource` config/result types and notes requiring implementation tests. Treat these as intended support tiers, not proven capabilities.
3. Formula-book terms mix persistent bytes, resident bytes, and spill bytes in some totals. A disk spill volume cannot be added to resident memory without a residency/buffering model. RSS, heap, allocator, and file-cache values can also overlap. A replacement needs disjoint accounting categories and simultaneous phase peaks.
4. The publication contract describes pin-before-use but does not close the resolve-pointer / acquire-pin / reclamation race. Atomic pointer replacement alone is insufficient: pin acquisition must interlock with GC, and crash durability needs directory/metadata ordering.
5. Result semantics are a memory contract. BFS `path_result_bytes` and parent/distance arrays cannot be replaced silently with a reached-node bitmap. Embeddings at N*d*w bytes cannot be made small by choosing a compact topology.
6. Binary Neo4j record layout is not established as necessary for wire/API compatibility. The OLTP contract conflates physical imitation with observable semantic obligations; transaction, value, cursor-result, and recovery behavior need proof, but exact record bits require a separately stated on-disk-compatibility goal.
